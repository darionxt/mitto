# The Runtime

The **Runtime** runs a **Page**'s scripts in a process of its own, on the **Engine Release**'s V8, while the Page's **Session** stays in the caller's process with its network, cookies and cache ([ADR-0009](adr/0009-a-process-for-each-page.md)). Terms in **bold** are defined in [CONTEXT.md](../CONTEXT.md). [building.md](building.md#build-the-runtime) says how the Page program is built. Until the release that ships the Runtime, the Page API is private, and a wheel that a release makes holds no Page program. [From Python](#from-python) says how the private API works.

## A Page and its process

Each Page is a process of the Page program, `mitto_page`, or `mitto_page.exe` on Windows. `mitto_page_open()` in the C API starts it from the directory that the library was loaded from, which is where a wheel puts both. Without a program there, as in a wheel that a release made, it fails with `ERR_FILE_NOT_FOUND`.

The library makes the channel first, then starts the program with its end of the channel and one argument, `--session=CHANNEL,PARENT`. `CHANNEL` names that end and `PARENT` is the ID of the process that holds the library. The program's standard input is the null device, and it shares standard output and error with the process that holds the library, so that what V8 or a sanitizer reports on a crash is not lost. It inherits nothing else:

| Host | The channel | What else the Page process inherits | The Page ends when the process that holds the library ends |
| --- | --- | --- | --- |
| macOS | One end of a socket pair, at descriptor 3 | Nothing: `posix_spawn()` closes every descriptor that it is not told to pass on | Its end of the channel reads the end of the stream. It also watches its parent with a `kqueue`, for when another process holds the library's end, such as one that the parent forked |
| Linux | One end of a socket pair, at descriptor 3 | Nothing: `//base` closes every other descriptor before it starts the program, and sets `PR_SET_NO_NEW_PRIVS` | The end of the stream, and the kernel's `PR_SET_PDEATHSIG`, which kills it when the thread that started it ends. So the library starts each Page from a thread that never ends |
| Windows | The client end of a named pipe, whose handle value the argument holds | Nothing: only that handle is in `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` | The pipe breaks. It also runs in a job object of its own, with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, which ends it when the last handle to the job closes, as when the process that holds the library ends |

On Windows the job also has `JOB_OBJECT_LIMIT_DIE_ON_UNHANDLED_EXCEPTION`, so that a crash ends the process at once rather than waiting for Windows Error Reporting, and the program starts hidden, so that a caller with no console gets no window. The named pipe has a random name under `\\.\pipe\LOCAL\`, one instance, and remote clients refused. Its end in the library is not inherited by any program, and the library opens the client end itself before it starts the Page, as Mojo's `PlatformChannel` does.

On Linux, a Page process holds about 18 MB of memory before a page loads. Besides its main thread and its I/O thread it runs V8's worker threads, one fewer than the machine has cores.

## What a Page process holds and reads

A Page process holds its end of the channel and its standard streams, and opens no file or socket of its own, so that Chromium's sandbox can hold it before the Runtime ships (roadmap, M10):

- ICU's whole data file and V8's startup snapshot are inside the program ([building.md](building.md#icus-data-and-v8s-snapshot)).
- What it would read of the machine and of its browser comes from the Session, in the start message below: everything of the Session's [Machine](persona.md#the-runtime) that a page reads, such as its time zone, processors, memory, display and its refresh rate, work area, window and network, and what the browser tells a renderer of itself, the user agent and the values of the user agent client hints of its Persona, and the languages of its `Accept-Language`. So ICU never reads `TZ`, `/etc/localtime` or the zone files. The `start` option of `mitto_page_open()` gives them, which Python fills from the Session's Machine, Persona and settings, and the library adds what `navigator.connection` gives. The Page sets the time zone and the locale as Blink sets the time zone that its browser reads, and its `navigator`, `screen` and window give the rest ([The window](#the-window)). The start also gives the runtime-enabled features and V8 flags of the Persona's Chrome Release ([persona.md](persona.md#what-a-page-of-each-persona-turns-on-and-off)), which a renderer of Chrome gets on its command line.
- V8's random numbers come from the system's random source through `//base`, which reads no file, as in Chrome's renderers.

What it holds is checked on Linux, where a test reads `/proc/<pid>/fd` of a Page that has run a script. It finds standard input on `/dev/null`, standard output and error as the test program's, the socket at descriptor 3, and the epoll and eventfd of the program's I/O thread, which name no file.

Before its `main()`, the dynamic loader of Linux opens the shared libraries of glibc, as it does for any program. After it, `strace` shows the Page reading `/sys/devices/system/cpu/online`, for how many threads V8 starts, and `/proc/self/maps`, which glibc reads to find the main thread's stack, and opening nothing else. Chrome's renderers read the same, and the sandbox of M10 has to allow them, as Chrome's does.

## Inside the Page program

The program runs V8 on its main thread, and reads the channel on a thread of its own. A Session's Page starts V8 once its start message has come, since V8 takes its flags before it starts and each isolate's runtime-enabled features are fixed when it is made: it sets the flags of every Page of the Engine Release, as Chrome's renderer sets them ([building.md](building.md#v8s-flags)), then the Persona's V8 flags from the start, starts V8 and makes the isolate with the Persona's features and the heap's limits that its Machine's memory gives. Given a script, the program starts V8 before it runs it, with the Engine Release's flags and the limits of 8 GiB, the memory of the most common Machine. The I/O thread checks each message, hands scripts to the main thread in the order they came, and sends their results back. Because it reads while a script runs, the process ends as soon as the channel closes, even in the middle of a script that never ends.

As each of Chrome's processes does, the program sets `//base`'s features when it starts, each to its default, since a Page gets none of the browser's. So `base::RandBytes()`, which `crypto.getRandomValues()` fills a view with, takes BoringSSL's random bytes, as Chrome's renderer does.

Each script runs in one context, so each sees what the ones before it left there. Its result is what `JSON.stringify()` writes for it, nothing for a value that it writes nothing for, such as `undefined` or a function, and what was thrown, as `Uncaught TypeError: ...`, for a script that throws or a result that cannot be written as JSON, such as a BigInt. When V8 runs out of memory, the program ends with exit code 3, which the library reports as running out of memory.

When the result is a promise, the result of the call is what the promise settles with, as when DevTools evaluates a script and waits for its promise: what it was fulfilled with, or `Uncaught (in promise) ...` and why it was rejected. The microtasks that the script queued have run by then, so a promise that they settle has settled. One that is still pending gets a handler, the call stays in progress, and the scripts after it run meanwhile. So a later script, a timer or a response can settle it, and results come in any order. Only a promise is waited for, and not another object with a `then` method.

The console is V8's own, as in Chrome, where V8 installs `console` and Blink hears of each call through V8's inspector. So the program starts an inspector, as Blink does for each isolate, and the inspector hands it each message, with its arguments written as V8 writes them for Chrome's log, separated by spaces, and the level of the method that wrote it. The inspector also gives `console` what it gives in Chrome, `console.createTask()` and, for a window's context, `console.memory` ([below](#what-chrome-adds-beyond-the-idl-files)). An error that nothing caught, in a script of the document, a timer, a microtask, an event listener or a mutation observer, or that `reportError()` reports, fires `error` at the window first, as [Errors at the window](#errors-at-the-window) says, and then goes to the Session as a console says it, `Uncaught TypeError: ...`, unless a listener canceled it. The program hears of each through V8's message listener, as Blink does, or reports it itself where it calls a page's function, with V8's message of it, which says where it was thrown. A promise rejected with no handler is reported as Blink reports it: the promises that a task leaves rejected are reported from a task of their own, which comes after the tasks queued before it, unless a handler has come by then, also the one that a call adds to the promise it waits for. That task fires `unhandledrejection` at the window, and the Session gets `Uncaught (in promise) ...` unless a listener canceled it. A script's console messages and the errors that it leaves uncaught reach the Session before its result, because results wait for those reports.

### The event loop

The main thread is the Page's event loop, a `base::sequence_manager::SequenceManager` on the real clock, with no virtual time, and with Blink's eleven task priorities ([`page_scheduler.h`](../native/page/page_scheduler.h)). Every task is one of its tasks: a script or a cookie answer from the Session, each step of a document's loading, each part of a response, each timer, and V8's own tasks for the main thread, such as its garbage collector's, which the program's `v8::Platform` posts to a queue of V8's, as gin's does for Chrome's renderers ([`page_platform.h`](../native/page/page_platform.h)). A task of the DOM has one of Blink's task types ([`event_loop.h`](../native/dom/event_loop.h)) and goes to the queue that Blink's frame scheduler makes for that type, at the priority that it gives it on a page that is visible: Blink's continuation of script loading at a very high priority, networking control at a high one, low-priority script execution at a low one, and every other task source of the HTML Standard, such as networking, DOM manipulation, timers, idle callbacks that time out, the Cookie Store's answers and Web Locks, at the normal priority. The scripts that the Session evaluates go to the inspector's queue, as DevTools' do, each part of a response to the loading queue, what belongs to no frame, such as the start and a document's loading, to a default queue, and the compositor has a queue at the normal priority where [a frame's](#animation-frames) rendering steps begin, which goes very high while rendering starves. Beside them, `scheduler.postTask()` and `scheduler.yield()` have a queue for each of their priorities, idle callbacks one that runs only when nothing else is ready, and the idle periods a control queue before all the others, ordered as Blink orders them: a task of a higher priority runs first, and tasks of one priority run in the order they were ready, whichever queue holds them. A timer of no delay is an immediate task, as Blink's `TimerBase` posts it, so it keeps its place among the tasks posted beside it. A parser that goes on once the script that it waited for is ready, and the next deferred script, run at the very high priority, as [Loading a document](#loading-a-document) says, and an async script of another site while a page loads at the low one.

Microtasks run as Blink runs them, with V8's `kScoped` policy: once the outermost script that the Runtime runs returns, which is the HTML Standard's clean up after running a script, and in a microtask checkpoint after each task, as Blink's scheduler runs one after each task. `queueMicrotask()` queues a function on V8's microtask queue, with promise jobs. A task that settles promises from C++, such as the end of a response, runs their reactions after it, not between them.

### Timers

`setTimeout()`, `setInterval()`, `clearTimeout()` and `clearInterval()` follow the HTML Standard's timer initialisation steps as Chrome runs them, in [`native/dom/dom_timer.cc`](../native/dom/dom_timer.cc), a port of Blink's `DOMTimer`:

- A timeout less than 0 is 0, and one that does not fit a `long` wraps, as Web IDL converts it.
- A timer set from a timer whose nesting level is 5 or more waits at least 4 milliseconds, so the seventh of a chain of `setTimeout(f, 0)` is the first that does. An interval grows to 4 milliseconds once it has repeated that often. Chrome counts the nesting level up before it compares it, which comes to the same.
- There is no clamp to 1 millisecond: `setTimeout(f, 1)` runs after a `setTimeout(g, 0)` set after it, as in Chrome, and `setInterval()` has none either, since `SetIntervalWithoutClamp` is on for stable.
- A timer shorter than 32 milliseconds runs on time, and a longer one when the thread wakes up anyway soon after, as Chrome posts them.
- A string runs as a classic script. An empty string sets no timer and gives 0, as in Chrome.
- IDs start at 1 and wrap at the largest `long`, skipping those in use. A timer's arguments go to its function, with the window as `this`.
- The timers stop with their window's context, when the Page loads a document.

### Idle callbacks

`requestIdleCallback()` and `cancelIdleCallback()` run as Blink's `ScriptedIdleTaskController` runs them, in idle periods that [`idle_helper.h`](../native/page/idle_helper.h) ports from Blink's `IdleHelper`. While a Page begins no [frames](#animation-frames), its periods are the long idle periods that Chrome has once a page expects none: each lasts until the next delayed task is due, and at most 50 milliseconds, and one that would be shorter than a millisecond waits a millisecond. A frame ends the idle period, and a short one lasts from the frame's end until the next vsync, as Blink's `WillBeginFrame()`, `DidCommitFrameToCompositor()` and `BeginMainFrameNotExpectedUntil()` have it, and long ones start again once frames stop, with `BeginFrameNotExpectedSoon()`. Idle tasks wait behind a fence that lets through only those posted before the period started, so the callbacks of a period share its end as their deadline, and one requested inside a period waits for the next, which starts when this one ends. Periods pause when no callback waits, and start again with the next request. `timeRemaining()` is coarsened as `performance.now()` is, and 0 past the deadline. A callback with a timeout runs as a task of its own once the timeout has passed, if it has not run by then, with `didTimeout` true. IDs start at 1 and wrap at the largest `long`. What a callback throws is reported as an uncaught error. Chrome's recording of these orders and deadlines is of a page that has loaded: while a page loads, Chrome draws frames and its idle periods end with them, and a Page begins frames only for its animation frame callbacks.

### Animation frames

`requestAnimationFrame()`, `webkitRequestAnimationFrame()`, `cancelAnimationFrame()` and `webkitCancelAnimationFrame()` run as Blink's `ScriptedAnimationController` and `FrameRequestCallbackCollection` run them, in [`animation_frame_controller.h`](../native/dom/animation_frame_controller.h), in the frames that [`begin_frame_source.h`](../native/page/begin_frame_source.h) begins as Chrome on Windows begins them for a visible page that asks for one. The Page lays nothing out, so a frame runs only the animation frame callbacks of the HTML Standard's rendering steps, and before them the events that the DOM queues for the next frame, as Blink's `Document::EnqueueAnimationFrameEvent()` queues a dialog's `close`, each with its microtasks.

- **When.** Frames begin at the vsyncs of the display of the Page's [Machine](persona.md#the-runtime), a period apart that Chrome works out from the refresh rate in whole microseconds, so 16,667 at 60 Hz and 6,944 at 144 Hz, at a phase of the Page's own. A request while frames do not come gets a missed frame at once, which has the time of the last vsync, as Viz sends one to a compositor that starts to observe it, so its time can be up to a period before the request. While frames come, the next begins with the first vsync whose BeginFrame reaches the compositor after the last frame ended, which is about as long after the vsync as a frame takes to start, so a display faster than that still gets a frame at each vsync. Frames stop with the next BeginFrame after a frame that asked for no other. A frame starts 1.2 milliseconds after its vsync, and a missed one 0.15 milliseconds after the request, as Chrome 157.0.8103.51 did on macOS, headless.
- **Where.** Each frame is a task of the compositor's queue, at the normal priority, and at a very high one once a task ends 100 milliseconds or more after the last frame, until the next frame, as Blink keeps rendering from starving. A frame that waits behind a busy task runs late with the time of its vsync.
- **What a callback gets.** The frame's time since the start of the navigation that loaded the document, coarsened to 100 microseconds with a secret of its own, as Blink's `PageAnimator` gives it, so whole tenths of a millisecond, such as `162.4`, and never less than the frame before. Every callback of a frame gets the same time. A callback of `webkitRequestAnimationFrame()` gets that time on the wall clock, in milliseconds since the Unix epoch, as precise as the clock is.
- **How.** Each callback that waits when a frame begins runs in it, in the order they were asked for, with undefined as `this`, its microtasks after it, and what it throws reported as an uncaught error. A callback asked for in a frame runs in the next. One that an earlier callback of its frame cancels does not run. A `scheduler.yield()` in a callback inherits what the task that asked for it had, as `FrameRequestCallback`'s task attribution carries it.
- **IDs** start at 1 for each document, shared by both forms, as in Chrome, and a request gives 0 once the window's context has gone.

[`tests/test_page_animation_frames.py`](../tests/test_page_animation_frames.py) holds a Page to what Chrome 157 gave for the same scripts, and to the period of its Machine's refresh rate.

### The scheduler

`scheduler.postTask()` posts its callback, after its `delay`, to the queue of its priority: its `priority` option, else that of its `TaskSignal`, else `user-visible`, which shares the normal priority with the HTML Standard's task sources. Its promise settles as the callback returns or throws, and rejects with the signal's reason if the signal aborts before the callback has returned. `scheduler.yield()` continues in a queue that comes before the tasks of its priority, which it inherits, with the signal, from the task it runs in, as Blink's task attribution carries it: a `postTask()` callback has its own, an idle callback the `background` priority, and V8 hands that state on to the promise reactions they leave, through the isolate's continuation-preserved embedder data ([`scheduler_task_context.h`](../native/dom/scheduler_task_context.h)). A timer or an event carries none, so a `yield()` there continues at `user-visible`, as in Chrome. A `TaskSignal` keeps the priority that it was made with, since `setPriority()` is a Known Gap.

### Web Locks and the Cookie Store

`navigator.locks` keeps Web Locks within the Page: [`lock_service.h`](../native/dom/lock_service.h) stands where Chrome's browser keeps an origin's lock group, with one group for each origin across the Page's documents, Chrome's order of grants, shared and exclusive modes, `ifAvailable`, `steal` and signals, and `query()` gives the held locks and the waiting requests by name, each with the document's client ID. What a document asks reaches the service from a task, and the grant comes back from another, as a Mojo message each way would, so a grant lands after a timer set beside its request, as in Chrome. Chrome shares an origin's locks across the tabs of a profile; a Page shares them across its own documents, the only clients it has.

`window.cookieStore` reads and writes the Session's cookies for the document, as Blink's `CookieStore` asks `RestrictedCookieManager`: the Page checks names, values, domains, with the public suffix list, and paths with Blink's messages before it asks, the Session makes and stores the cookie as `RestrictedCookieManager` does, always secure and never HttpOnly, and each promise settles from a task once the Session has answered ([The messages](#the-messages), 19 to 24). While a page listens for `change`, the Session tells the store of each change to the document's cookies that its script may see, and the store fires a `CookieChangeEvent`, whose `changed` and `deleted` are frozen arrays of `CookieListItem`s, each with the members Blink gives, in the order of their names. A document with an opaque origin, such as about:blank, gets a `SecurityError`, and so does the command line.

### Clocks

The clocks are coarsened as Chrome's are, against timing attacks, each with a secret of the process that decides where the clamped value steps to the next:

- `performance.now()` and `performance.timeOrigin` to 100 microseconds, as Blink's `TimeClamper` does for a context that is not cross-origin isolated, which a Page never is. `now()` counts from the start of the navigation that loaded the document, which the Session sends, and from when the context was made for about:blank. A Page's navigation starts when the caller opens the Page, before its process starts, as Chrome starts a tab's navigation before its renderer runs, so its fetch starts a few milliseconds later, as Chrome's does. Every time of [the Performance Timeline](#the-performance-timeline) is coarsened with the same clamper. So `performance.now()` gives multiples of 0.1, up to the rounding of a double, such as `52.80000000074506`.
- `Date.now()` and `new Date()` read the clock that the program's `v8::Platform` gives V8, coarsened to 5 microseconds as gin's `TimeClamper` does, which shows only within 5 microseconds of a millisecond's boundary.

Given a script on its command line instead of `--session=`, the program has no Session to start it, so its `navigator` and `screen` give empty strings and zeros, `devicePixelRatio` 1, and its frames come at 60 Hz. It runs the script, then its event loop until no task is ready and no timer, idle callback, animation frame callback or event, or scheduler task waits, that of an `AbortSignal.timeout()` among them, and prints the result, which [building.md](building.md#build-the-runtime) describes: what a promise that the script returns was fulfilled with, or why it was rejected, or that it never settled. There, `fetch()` fails, for want of a Session. Either way, the context has the interfaces that the Runtime implements, as the Page's runtime-enabled features expose them ([the bindings](#the-bindings)).

### What Chrome adds beyond the IDL files

Chrome's renderer puts objects on a page that no Web IDL file declares, and Blink gives some values from its own state. A Page has them as Chrome 157 shows them on a top-level page, which [`tests/test_page_renderer.py`](../tests/test_page_renderer.py) holds it to:

- **`window.chrome`**, a plain object on the global object, from [`native/page/chrome_object.cc`](../native/page/chrome_object.cc). Chrome adds it once the global object has what Window's template gives it and before what the context decides, so it comes right after V8's builtins, `Temporal` and `WebAssembly`, and before members such as `crashReport` and `cookieStore`, and so does the Page's.
  - `loadTimes()` and `csi()`, from `chrome/renderer/loadtimes_bindings.cc`, are functions with no name and a `prototype`. Each call gives a new object, whose properties ignore what a page assigns to them.
    - `loadTimes()` gives the navigation's times in seconds, read from `performance.timing`, as Chrome's reads Blink's `WebPerformance`: `requestTime` and `startLoadTime` its `navigationStart`, `commitLoadTime` its `responseStart`, the first byte of the response's headers, `finishDocumentLoadTime` and `finishLoadTime` the ends of `DOMContentLoaded` and `load`, each 0 until it has come.
    - `firstPaintTime` stays 0, because the Page paints nothing, where Chrome's comes once a page has painted. That is a Known Gap.
    - `navigationType` is `"Other"`, as for a typed URL. `wasFetchedViaSpdy`, `wasNpnNegotiated`, `npnNegotiatedProtocol` and `connectionInfo` are the response's connection, which the Session sends.
    - `csi()` gives `startE` and `onloadT`, the start and the end of `DOMContentLoaded` in milliseconds, `pageT`, the time since the start, and `tran`, 15.
  - `app` is what Chrome's extensions system gives every web page that no installed app covers:
    - `isInstalled`, `false`, and `getIsInstalled()`, also `false`;
    - `getDetails()`, `null`, and `runningState()`, `"cannot_run"`;
    - `installState()`, which calls a callback with `"not_installed"` from a later task;
    - the enumerations `InstallState` and `RunningState`.

    Each method throws the extensions system's `TypeError`, such as `Error in invocation of app.getDetails(): `, for an argument its signature does not take. Members that only an installed extension's pages or the Web Store get, such as `chrome.runtime`, are not there.
- **`performance.memory` and `console.memory`** give Blink's `MemoryInfo`, a new object each time, with the sizes of V8's heap, from [`native/dom/memory_info.cc`](../native/dom/memory_info.cc). `MemoryInfo` has no interface object, so a page reaches its prototype only through one.
  - `performance.memory` is precise while the document is at an HTTP or HTTPS URL, as Chrome's site isolation locks a desktop renderer to the site of its document, and read at most once in 50 milliseconds.
  - `console.memory` is always bucketized: each size rounded up to one of 100 sizes from about 10 MB to about 4 GB, read at most once in 20 minutes.
  - Both read one cache, as in Blink, so a reading of one precision stands for the other until the other's time is up.
  - `jsHeapSizeLimit` follows the Machine's memory ([building.md](building.md#what-chromes-renderer-sets-up-on-its-isolate)). The used and total sizes follow what the page has done, and the Normal Form drops them.

What else Chrome's renderer sets up for V8, such as `SharedArrayBuffer`, `WebAssembly.compileStreaming()` and `Atomics.wait()`, is in [building.md](building.md#what-chromes-renderer-sets-up-on-its-isolate).

## The channel

The channel is the native core's own, on `//base`, and not Chromium's Mojo ([ADR-0009](adr/0009-a-process-for-each-page.md)). In the library, the network thread reads and writes it, on its message pump: with a watch on the socket on macOS and Linux, and with overlapped reads and writes on the pipe, which complete on the thread's completion port, on Windows. The Page program does the same on its I/O thread. Neither ever blocks on it: what the system cannot take yet waits in memory.

Each message travels as a frame: the size of its payload and its type, each a 32-bit little-endian number, and then the payload. Each side refuses a frame whose payload is larger than 16 MiB, so that the other cannot make it hold more for one message. So a script can be at most 16 MiB less 8 bytes, and a result whose JSON is larger fails with a message that says so.

[`native/page_messages.h`](../native/page_messages.h) holds the frames and the messages, which both programs build. [`native/page_channel.h`](../native/page_channel.h) holds the channel, with one file for macOS and Linux and one for Windows.

### The documents of a Page

Each message that a document sends names the document by an ID that the Page gives it, from 1 up, never again for another, as [#261](https://github.com/darionxt/mitto/issues/261) decided for a Page's documents, frames and workers. The Page tells the library of each document it makes, with a message of type 70, before anything that the document sends: about:blank first, as 1, then the document of each navigation's response, and of each frame, under the document that holds the frame, and of each dedicated worker, with a message of type 100, under the context that started it. Documents and workers share the IDs. The library keeps the URL that it loaded each at, the final URL of the navigation's response, a frame's initial about:blank, which has its parent's origin, or a worker's script's final URL, and works out what a message of the context asks for from that and from the frame tree, never from what the Page says: the Initiator and `Referer` of its requests, the top-level frame that partitions them and the site for cookies, which a frame of another site than the top-level one, or under one, has none of, the cookies that a document's `document.cookie` and `CookieStore` read and write, and the origin of its broadcasts. A worker's requests start from its script's URL, in its creator's frame, with no client hints, as #265 recorded Chrome's, and a worker sends no cookie message, load, same-document navigation or navigation. A top-level document takes the place of the one before it and of everything under it, which the library forgets, a frame's navigation that of the frame's document that it names, and the channel's order puts every message of the old document before it, so a request that the old document asked for keeps the old document as its Initiator while the new one loads. A frame's document that its element lets go, or a worker that ends, goes with a message of type 101. Each context that goes lets its keepalive requests go on without it. The Page program makes no frame or worker yet; the library takes them for [#285](https://github.com/darionxt/mitto/issues/285) and [#289](https://github.com/darionxt/mitto/issues/289). A frame's initial about:blank and a worker of a blob: URL speak for their origin in what they ask of cookies, broadcasts and the Cache API. A context's Cache API puts that wait for a body fail when it goes. Known Gaps: a worker of a data: URL has an opaque origin and so no request, and a frame's Cache API has a first-party storage key, where Chrome partitions a frame of another site. In Chrome, the browser gives each document a pipe of its own to the network service, whose requests it trusts only as that document's, which is what the ID stands for on a Page's one channel.

A body travels only as far as the Page has given credit for it. Each request starts with 64 KiB of credit, as much as the library holds of a request's body for a caller, and the library reads more of the body from `//net` only once the Page has given credit back for what it took. So a Page that takes its bodies slowly, as a parser that waits for a script does, slows the server down, as a slow reader of a request does. The library answers questions for cookies in the order they come, and the channel keeps the order of everything, so a read of `document.cookie` after a write sees it, and so does a request that the Page asks for after it.

Both programs come from one tree and ship together, so the version on both sides must be the same, and it changes with any change to the messages. Each side refuses, with a Refused message that says why:

- a hello of another version, and any message before the hello;
- a type that it does not know, or one that only goes the other way;
- a payload that is not what its type says, such as text that is not UTF-8 or a console message of an unknown level;
- a frame larger than the channel carries;
- for the library, a result of a call that is not in progress, a message of a context that the Page has not told of, or that has gone, a document or worker whose ID is not larger than the one before, a top-level initial about:blank after another document, a document whose parent is not one of the Page's documents, a document of a navigation whose response the library has not sent or that has a document already, or of a frame's navigation under another parent than its frame's, a frame's navigation that does not name a frame's document, a worker whose creator is not one of the Page's contexts, whose script is not the response of a request of Kind `worker` of that creator, or whose blob: URL is of another origin, a message that only a document sends from a worker, or a navigation that a worker starts, the top-level document going while the Page stays, a request whose number is not larger than the one before, more than 2700 requests at once, as Chrome's network service allows a renderer process, credit for a request that the Page has not asked for, or for more of a body than the library sent, or a cancel of one that it has not asked for, or a cookie of the `CookieStore` for a domain that the document's host does not match, which the Page checks first, or a broadcast from a Page with no document of an HTTP or HTTPS origin, whose channels no other Page shares, or a same-document navigation to a URL of another origin than the document's, unless only its fragment changes, or a question of the Cache API from a document that is not of an HTTP or HTTPS origin in a secure context, or whose number is not larger than the one before, a call of a cache that the Page has not opened, a put that Blink would not send, such as one of a `POST` or with `Vary: *`, a part of a put's body that the library did not ask for, or a read of a stored body that it did not give. Also a request whose method is not a token or is forbidden, such as `TRACE`, whose header lines are not valid or include a forbidden request header, such as `Cookie` or one that starts with `Sec-`, that has a body with `GET` or `HEAD`, that asks for a script or a navigation with any of these, or that is not a navigation and has a navigation's flags: Chrome's network service refuses such a request from a renderer too, and a Page that sends one is not the Runtime's;
- for the Page, a second start, a script before the start, a start that lacks a key or has another, or a value that a Machine, a Persona or Chrome's network estimate cannot have, a time zone or locale that ICU does not know, a name in its features that is not a runtime-enabled feature, a response whose `rtt` or `downlink` Chrome cannot give, or whose timing //net cannot give, such as a negative time or more than 20 redirects, a response or body of a request that is not in progress, more of a body than it has given credit for, or cookies or an answer for a question, of `document.cookie` or of the `CookieStore`, that no script waits for, or a broadcast before the start, an answer of the Cache API that no script waits for, a request for a put's body that no put holds, or more of a stored body than it has given credit for.

The library reads what a Page sends as hostile input: a Page runs a site's scripts. It checks each frame field by field before it acts on it, and the fuzz target `page_messages_fuzzer` feeds any bytes to that code ([building.md](building.md#sanitizer-builds-and-the-fuzz-target)). When the library refuses, it also kills the Page process, rather than trusting it to end.

A refusal ends the Page, and its calls fail with `MITTO_PAGE_ERROR_REFUSED` and a message that says which side refused what, such as:

```text
the library refused a message from the Page: the Page speaks version 99 of the messages, and the library speaks 1
the Page refused a message from the library: the time zone "Mars/Olympus_Mons" is unknown
```

## The C API

[`mitto.h`](../native/include/mitto/mitto.h) has the Page's calls, which return at once, and its events, which wait in a native queue as a request's do ([ADR-0003](adr/0003-c-abi-and-ctypes.md)):

- `mitto_page_open()` opens a Page on a Session, with versioned JSON options, whose `start` is what the Page starts with. An unknown key is refused. With `url`, the Page navigates there once it opens, as [Loading a document](#loading-a-document) says, with what each Request Kind sends in `requests`.
- `mitto_page_evaluate()` sends a script and stores the number of its call. Each call gets one `MITTO_PAGE_EVENT_EVALUATED` event, with the result as JSON or an error.
- `mitto_page_next_event()` takes the next event, blocking for as long as the caller says, and `mitto_page_event_free()` releases it. Beside `MITTO_PAGE_EVENT_EVALUATED` and `MITTO_PAGE_EVENT_ENDED`, a Page has a `MITTO_PAGE_EVENT_CONSOLE` event for each console message, with its level, a `MITTO_PAGE_EVENT_UNCAUGHT_ERROR` event for each error that no script caught, a `MITTO_PAGE_EVENT_KNOWN_GAP` event with the name of each Known Gap, the first time each document reaches it, a `MITTO_PAGE_EVENT_NAVIGATION_STARTED` event, with its URL, when its document starts a navigation to another document, a `MITTO_PAGE_EVENT_NAVIGATED` event for each navigation, the one that opened the Page and each that started, in order, once the Page has made the document of its response, after every event of the old document, with the document's URL and status, or when it has ended with no document, with `ERR_ABORTED` and the status, or another took its place first, with `ERR_ABORTED` and status 0, or has failed, with the net error, a `MITTO_PAGE_EVENT_URL_CHANGED` event, with the new URL, when a navigation within the document changes its URL, and a `MITTO_PAGE_EVENT_LOADED` event when the window's `load` event has been dispatched.
- `mitto_page_end_waits()` ends each wait of `mitto_page_next_event()` on another thread, and makes each later one return at once if no event waits, so that the thread that closes a Page can stop another that waits, as `mitto_session_end_waits()` does for a Session.
- `mitto_page_process_id()` gives the ID of the Page's process.
- `mitto_page_close()` closes the Page.

At most 1000 console messages and uncaught errors of a Page wait untaken, and at most 32 MiB of their text, so that a Page that writes without end cannot fill the memory of the process that holds the library. V8's inspector keeps as many console messages for DevTools. The library drops the ones past that, and the next one that has room comes after a console warning that says how many it dropped. Results and the end of the Page are never dropped.

A Page's events list its handle in the Session's list of what is ready, beside its requests' events. So the file descriptor that an asyncio caller watches on macOS and Linux, and `mitto_session_wait_for_event()` on Windows, wake for both. `mitto_session_next_ready()` names the handle and says whether it is a request's or a Page's.

## How a Page ends

Each way of ending reaps the process, so none is left behind:

- `mitto_page_close()` closes the channel. The Page process reads the end of the stream and ends at once. The call waits for that, for up to 2 seconds before it kills the process, and returns once the process has gone.
- `mitto_session_destroy()` does the same for each Page of the Session. Each Page gets a `MITTO_PAGE_EVENT_ENDED` event with `MITTO_PAGE_ERROR_SESSION_DESTROYED`, and its handle stays valid until it is closed.
- When the process that holds the library ends without either, the Page process ends as the table above says.
- When the Page process crashes, runs out of memory or is killed, the library reads the end of the stream on the network thread, and a worker thread reaps the process to learn how it ended. Each call in progress then fails with `MITTO_PAGE_ERROR_PROCESS_ENDED`, a `MITTO_PAGE_EVENT_ENDED` event follows, and each later call fails the same way. The message says how the process ended, such as `the Page process was ended by signal 9` or `the Page process ran out of memory`. The Session's other Pages and requests go on.

On macOS and Linux the library reaps its Page processes with `waitpid()` on the process's ID. A caller that waits for any child, or ignores `SIGCHLD`, can take a Page's exit status first. The library then says that the process ended and that something else in the process took its exit status.

## The bindings

What a page's scripts can reach of the Web's interfaces, and how, is part of its **Script Fingerprint**. So the Runtime's V8 bindings come from the Engine Release's Web IDL files, as Chrome's do, and are written by a generator of mitto's own, [`native/bindings/bindings_generator`](../native/bindings/bindings_generator), which GN runs on every build of the Runtime. Blink's own generator, `bind_gen`, writes code for Blink's classes, which mitto does not have. The generator follows `bind_gen` for everything a page can see: which properties each object has and in which order, their attributes, names and `length`s, and the errors that each call throws, with Chrome's messages. Each module names the files of Blink's that it follows on its `Upstream:` lines.

### How the generator works

It runs in four steps, all in [`native/bindings/generate_bindings.py`](../native/bindings/generate_bindings.py) and the package next to it:

1. **Read.** Blink's scripts build the [Web IDL database](building.md#the-web-idl-database) from the IDL files of every interface that Chrome exposes to pages, with their partial interfaces and mixins merged in. The generator loads it with Blink's own `web_idl` package and reads every definition into a model of its own ([`web_idl_reader.py`](../native/bindings/bindings_generator/web_idl_reader.py), [`model.py`](../native/bindings/bindings_generator/model.py)): interfaces, namespaces, dictionaries, callbacks, enumerations, and each of their members, types and extended attributes. It reads all of them, whether or not the Runtime implements them yet, and it refuses anything it does not know, with a message that names it and where it is: a kind of definition, a type, or an extended attribute that [`extended_attributes.py`](../native/bindings/bindings_generator/extended_attributes.py) does not list. That file gives each of the 73 extended attributes that the database of 157.0.8103.39 uses a role: what it changes for a page, or that only Blink's implementation reads it, such as `[Measure]`. So when an Engine Release brings a construct that nobody has looked at, the build stops with its name, instead of writing bindings that are wrong.
2. **Plan.** For every interface, [`install_plan.py`](../native/bindings/bindings_generator/install_plan.py) works out the own properties of its interface object, prototype and instances in the order that Chrome installs them. `bind_gen` installs the members that are always there on V8's templates first, then those behind a runtime-enabled feature, and later, on each context's objects, those that the context decides, such as `[SecureContext]` members. V8 adds `constructor` to the prototype between the two. Within each of these, Blink installs the attributes, then the constants, then the operations, which `web_idl` sorts by name, with the members of one condition together. `[LegacyUnforgeable]` members go on each instance, not configurable. Chrome's renderer takes the objects of `Window`, `Document`, `HTMLDocument`, `Node`, `EventTarget` and `WindowProperties` from its V8 context snapshot, which holds only the members that are always there, so for these the members behind a feature come last, on each context's objects.
3. **Write.** It writes into `out/runtime/gen/mitto/bindings` the bindings of every interface, namespace and callback interface that a Page's global object exposes, and of each ancestor of one, in one of two forms:
   - For each interface that has a C++ class in the Runtime, [`cpp_writer.py`](../native/bindings/bindings_generator/cpp_writer.py) writes `v8_<interface>.h` and `.cc`: a callback for each attribute, operation and constructor, and the function that installs them on the interface's templates in the order of the plan. It converts values as Web IDL says, in the order of `bind_gen`'s callbacks: V8's signature check of the receiver, which throws "Illegal invocation"; then for a constructor that it is called with `new`; then the number of arguments; then each argument in turn ([`cpp_types.py`](../native/bindings/bindings_generator/cpp_types.py)). It handles only the types and extended attributes that those interfaces use, and refuses any other there, naming it: adding a class may mean teaching it more.
   - For every other, [`table_writer.py`](../native/bindings/bindings_generator/table_writer.py) writes a table: its `WrapperTypeInfo` and each of its own properties in the order of the plan, with its kind, attributes, `length` and condition. [`interface_table.cc`](../native/bindings/interface_table.cc) installs a table on the construct's template, and on each context's objects for what the context decides, as `bind_gen`'s install functions do. A table holds data and no code, so the thousand or so interfaces without a class cost the Page program under 1 MB and their build a few seconds ([building.md](building.md#times-and-sizes)). The tables go into a fixed number of files, `interfaces_without_class_<n>.cc`, which [`generated_files.gni`](../native/bindings/generated_files.gni) names, so that GN knows them before the generator runs.

   It also writes the dictionaries and unions that the classes' bindings use, the table of runtime-enabled features, and the function that sets up a Page's global object. The generator writes a file only when its content changes, so a change to the generator or to `interfaces.gni` compiles again only the files it changes.
4. **List.** It writes `web_idl_listing.txt`, every interface and member that it planned, one per line, with the features and conditions each is behind. The release routine compares it between two Engine Releases ([releasing.md](releasing.md#2-check-out-the-new-engine-release)).

A page sees every interface, namespace and callback interface that Chrome exposes on `Window`, as [ADR-0008](adr/0008-v8-and-bindings-from-web-idl.md) has it, behind the features and conditions of each: 1,061 in the listing of 157.0.8103.39. Those with a C++ class are in [`native/bindings/interfaces.gni`](../native/bindings/interfaces.gni), and every member of one without a class is a Known Gap. Each class is `mitto::<interface>` in [`native/dom`](../native/dom). A member whose behaviour the Runtime lacks is a **Known Gap**: its binding is installed as Chrome's is, so the shape matches, and [What a Known Gap does](#what-a-known-gap-does) says what happens when a page calls it. An entry there either lists its Known Gaps in `missing`, as `EventTarget` does for `when()`, whose `Observable` the Runtime does not have, or lists in `implemented` the members its class has, so that every other member is a Known Gap, as the DOM's large interfaces do. `get x` there names the getter of an attribute alone. The generator gives a reflected attribute, `[Reflect]`, its behaviour itself, through the element's content attribute, with the accessors of the element that `bind_gen`'s `_make_reflect_accessor_func_name()` picks: a string, `DOMString` or `USVString`, with `[LegacyNullToEmptyString]` or without, gives the content attribute or `""`; a nullable string, such as the ARIA attributes of `Element`, gives null for a missing one, which null removes; a boolean, whether it is there; a `long`, Blink's `GetIntegralAttribute()`, the HTML Standard's rules for parsing integers, and 0 for one that is missing or does not parse; an `unsigned long` the same, with 0 for a negative value, and sets 0 for a value above 2147483647, as `SetUnsignedIntegralAttribute()` does; and one with `[URL]` the content attribute without its leading and trailing HTML spaces, resolved against the document's base URL, or as it is if it does not resolve, and `""` for a missing one, as `GetURLAttribute()` does. One that `[ReflectOnly]` limits to its keywords, which may be nullable, such as `crossOrigin` or `fetchPriority`, gives the content attribute in lower case if it is one of them, and otherwise what `[ReflectMissing]`, `[ReflectEmpty]` or `[ReflectInvalid]` say, or null or `""`, as `bind_gen`'s `make_reflect_process_keyword_state()` writes it, and null removes the content attribute of a nullable one. The setter of a reflected boolean or `DOMString` of an element with `[CEReactions]` and nothing else that has a side effect throws "1 argument required, but only 0 present." when it is called with no argument, as the setter that `bind_gen`'s `optimize_element_cereactions_reflect()` shares does; every other setter converts the missing argument as `undefined`, as `bind_gen`'s leave out the check. A reflected `Element`, such as `popoverTargetElement`, stays with its class. The generator and leaves an indexed or named property operation that is a Known Gap out, so that a page reads nothing through it.

For Chromium 157.0.8103.39, the generator reads the whole database and writes everything in about 3 seconds, and the listing has 20,237 lines, about 1.2 MB.

### What a Known Gap does

A Known Gap does what the owner chose on 2026-11-12, in [#208](https://github.com/darionxt/mitto/issues/208), whose comment compares the options. Before, it threw `TypeError: Not implemented.`, which Chrome never says, so one caught error told a page that it did not run in Chrome, and the page's script stopped where Chrome's goes on. In short, it does what Chrome's binding does up to the call into Blink, tells the Session, and gives its type's default. Its callbacks are in [`known_gap.cc`](../native/bindings/known_gap.cc), the same for an interface with a class and one without, and they read the member's types and overloads from tables that the generator writes into `idl_types.cc` ([`type_tables.py`](../native/bindings/bindings_generator/type_tables.py)):

1. **Chrome's checks first.** In the order of `bind_gen`'s callbacks, with Chrome's messages, as the binding of a member with behaviour does, it:
   - checks the receiver;
   - for a constructor, checks that it is called with `new`;
   - checks the number of arguments;
   - resolves the overloads;
   - converts each argument as Web IDL says.

   For an operation or an attribute that returns a promise, an error from any of these rejects the promise, a wrong receiver among them: Chrome gives such a member no V8 signature check, and checks the receiver in the call instead. An operation whose IDL declares several overloads, even if the feature set has only one of them, goes through `bind_gen`'s overload dispatcher first, which checks the number of arguments and the distinguishing argument before the overload checks the receiver, so `CookieStore.prototype.set.call({})` rejects with "1 argument required, but only 0 present.". So a wrong argument fails as it does in Chrome, and the page's own getters, iterators, `valueOf()` and `toString()` run as they run in Chrome. The converted arguments are thrown away: only the call into the Runtime's C++ is missing. [`idl_conversions.cc`](../native/bindings/idl_conversions.cc) converts each type as Blink's `NativeValueTraits` do, with their messages, a union as `bind_gen`'s `union.py` tries its members, and a dictionary's members in order, with the member being read in front of an error. It resolves overloads as `bind_gen`'s overload dispatcher does: the items of Web IDL's effective overload set that take as many arguments as the call gives, and among them the one that the value of the distinguishing argument selects, by the same tests in the same order. A call that no overload takes throws "N arguments required, but only M present." with the fewest that any overload needs, or else "Overload resolution failed.".
2. **A report.** It tells the Session the first time a document reaches it after its arguments have converted, named as the listing names it, such as `Navigator.prototype.getBattery`, or `new Highlight` for a constructor. The bindings remember for each document which they reported, and the Page sends each report to the Session as a Known gap message, which reaches a caller as a `MITTO_PAGE_EVENT_KNOWN_GAP` event and Python as the Page's `known_gaps`. Chrome's use counters count a feature the same way, once for each document (`UseCounterImpl::Count()` in `third_party/blink/renderer/core/frame/use_counter_impl.cc`). A Known Gap inside a member's behaviour, such as a selector that needs more than simple selectors, reports the same way. The generator also marks each Known Gap in `web_idl_listing.txt`, so that each build writes all of them down, including those that no Parity Check sees.
3. **Its type's default.**

   | Member | What it does |
   | --- | --- |
   | Getter | Gives the value that its setter last stored on that object, or else its type's default |
   | Setter | Stores the converted value for the getter |
   | Operation | Returns its return type's default, a new object for an interface |
   | Operation that returns a promise | Returns a promise resolved with the default of the promised type |
   | Constructor | Returns an object of the interface with nothing behind it |

   The one exception, which the owner chose on 2026-11-12: a `toJSON()` that returns an object gives what Web IDL's default toJSON steps collect, so that a page sees Chrome's keys. It gives a new object with each attribute of a JSON type of the interface that declares it and of each ancestor that declares a `toJSON()` too, ancestors first, each read through the object as a page reads it. Enumerations count among the JSON types, as Blink's own `toJSON()` methods include them. So `JSON.stringify(new DOMRect())` gives Chrome's `{"x":0,"y":0,"width":0,"height":0,"top":0,"right":0,"bottom":0,"left":0}`. Blink has no default `toJSON()` of its own: each class writes one.

   A type's default is:
   - `null` for a nullable type;
   - `false`, 0 or `""`;
   - an empty array for a sequence or a frozen array;
   - `undefined` for `any`;
   - the first value of an enumeration;
   - for an interface, an object of that interface with nothing behind it, whose members are Known Gaps too.

   A getter gives the same such object each time on one receiver, unless the IDL says `[NewObject]`. An iterable, maplike or setlike declaration on an object with nothing behind it iterates over nothing: its `entries()`, `keys()` and `values()` give an iterator of Chrome's shape, whose prototype holds `next()` and the iterator's name for `@@toStringTag`, such as "URLSearchParams Iterator", and inherits from V8's `%IteratorPrototype%`, or its Map, Set or async iterator prototype, and whose `next()` is done at once. The generator writes the table of each such iterator itself, since Blink's database merges them into their interfaces.

Some members follow other rules:

- **Event handler attributes** are not Known Gaps. The generator gives them Chrome's behaviour, as it does for reflected attributes. The getter gives `null` until a handler is set. The setter stores any object, and turns anything else into `null` without throwing, as `JSEventHandler::CreateOrNull()` does. The handler is a listener of its EventTarget ([`event_handlers.h`](../native/dom/event_handlers.h)): it joins the listeners the first time it is set, keeps its place when it is set again, and goes when it is set to `null`, as the HTML Standard's event handlers do. A dispatch calls it with the current target for `this` and the event for its argument, does nothing for one that cannot be called, and cancels the event when it returns `false`, as Blink's `JSEventHandler::InvokeInternal()` does. For an `ErrorEvent` of type `error` at a window, `onerror` gets the HTML Standard's five arguments instead, the event's `message`, `filename`, `lineno`, `colno` and `error`, and returning `true` cancels it. An `HTMLBodyElement`'s handlers of the window's events, such as `onload` and `onerror`, are its window's. A handler written in a content attribute, such as `<body onload="...">`, is not compiled yet, and neither is the special handling of `beforeunload`, an event that the Runtime does not fire.
- **A stringifier attribute's `toString()`**, such as `URL`'s for `href`, gives what the attribute's getter gives, the value its setter stored among it, as Blink's `toString()` is that getter.
- **An attribute's setter** ignores a string that is not one of its enumeration's values, as Web IDL says, and one with `[PutForwards]` sets the attribute it names on what the getter gives, as `bind_gen`'s setters do. A setter of a nullable type, a dictionary, `any` or an event handler called with no argument throws "1 argument required, but only 0 present.".
- **An object of an interface without a class** whose nearest ancestor with a class is `EventTarget` or `Event` has an object of that class behind it, which the DOM makes ([`objects_behind.h`](../native/dom/objects_behind.h)), so that `addEventListener()` and `dispatchEvent()` work on a `FileReader`, and `type` and `bubbles` on a `CustomEvent`, which its constructor's `type` and `EventInit` give. Its own members stay Known Gaps.
- **An event's constructor** sets the attributes that its init dictionary names, given or by their defaults, as the DOM Standard's inner event creation steps do and each of Blink's event classes does: `new PointerEvent('pointerdown', {pressure: 0.5}).pressure` is 0.5, and its `width` 1, `PointerEventInit`'s default. Each such attribute's getter gives that value from then on, as what a setter stored. A sequence becomes the attribute's frozen array, and a dictionary an object of the page's with its members in order, as Blink's `ToV8` makes them. A member whose type is not the attribute's, such as `TouchEventInit`'s sequence of `Touch` for `TouchEvent`'s `TouchList`, initializes nothing, and an attribute that Chrome works out instead, such as `MouseEvent.x` or `PointerEvent.altitudeAngle`, keeps its type's default.
- **An object of a class that a Known Gap may make**, one that [`interfaces.gni`](../native/bindings/interfaces.gni) marks `made_by_known_gaps`, is what the class's `CreateForKnownGap()` makes with nothing given: an empty `HTMLCollection` for `document.getElementsByTagName()`, a `DOMRect` of zeros for `getBoundingClientRect()`, an `EventCounts` with Chrome's 36 types for `performance.eventCounts`. An interface without a class whose nearest class is such a class gets one of its objects behind it the same way, as `HTMLFormControlsCollection` gets an empty `HTMLCollection`. So giving an interface a class takes nothing away from the Known Gaps that give its objects.
- **The generator refuses by name** a Known Gap whose default would be unsafe or impossible:
  - a member of `SubtleCrypto`, whose default would be a predictable digest or key;
  - an attribute or operation that gives an object of an interface that has a C++ class that a Known Gap may not make, whose class's members would find no object behind it.

  Each of these needs behaviour, or an outcome written by hand. Until it has one, it keeps `TypeError: Not implemented.` ([`known_gaps.py`](../native/bindings/bindings_generator/known_gaps.py)), and the listing marks it "Known Gap, refused". An object that a Page has no bindings for, such as one of an interface exposed only to workers, is refused the same way. For Chromium 157.0.8103.39, 78 members are refused.
- **The members that pages call most** get behaviour, or Chrome's outcome for the Page's state, written by hand, unless the default already is Chrome's outcome. These are the members used on at least 1% of page loads, by Chrome Platform Status's use counters. Chrome's outcome is the one for a Machine that has granted no permission, has only the devices it claims, and has no user activation. For example, `navigator.permissions.query()` gives `"prompt"`, where the first value of `PermissionState` would say `"granted"`. Where Chrome waits for a person, the outcome may be a promise that never settles, as `getUserMedia()` waits at its prompt. A member written this way is no longer a Known Gap. [The members pages call most](#the-members-pages-call-most) lists them, with what each gets.

The defaults keep a page's script running where Chrome's runs, and with it the requests the script makes. They are often Chrome's own values too. In a walk of a new page in Chrome 157, 85% of the getters within three steps of `window` gave their type's default, every event handler among them. A Parity Check therefore shows a Known Gap only where its default differs from Chrome's value.

### What the bindings run on

The generated callbacks and tables call a small runtime in [`native/bindings`](../native/bindings), on V8's own API, as Blink's `platform/bindings`:

- A Page's global object gets each interface object, namespace object, `[LegacyWindowAlias]` and `[LegacyFactoryFunction]`, such as `Image`, as a lazy data property that is not enumerable, as Blink's `IDLMemberInstaller::InstallExposedConstructs()` installs them: V8 makes the object the first time a page reads it, and the property is a data property from then on ([`idl_member_installer.h`](../native/bindings/idl_member_installer.h)). Those that are always there go on the template of the global object, and V8 installs a template's lazy data properties before its other properties, last first, as it does in Chrome. So `Object.getOwnPropertyNames(window)` lists V8's builtins, then the interface objects from `Option`, `Image` and `Audio` back to `AbortController`, then the members of `Window`, then what the context decides, as Chrome's does.
- Each context makes an interface object once, with its parent's for its own prototype, and installs on it and its prototype what the context decides, before a wrapper of the interface or anything else can reach them, as Blink's `V8PerContextData::ConstructorForType()` does. A namespace object is made each time its property is read, which happens once.
- The Runtime's C++ objects live on V8's C++ heap, cppgc, on which Blink's Oilpan is built, so that V8 collects them with the JavaScript objects that refer to them ([`script_wrappable.h`](../native/bindings/script_wrappable.h)). A wrapper holds its object through `v8::Object::Wrap()`, with the type tag that Blink's Web IDL database gives the interface, and the object holds its wrapper through a traced reference. A listener that a page adds is held the same way, so a target, its listeners and their closures go together when nothing else holds them.
- An argument converts to an object of an interface only if V8's template of that interface, or of one that inherits from it, made it, and its tag lies in the interface's range.
- What each context decides is installed once its interface objects exist: the `@@unscopables` of a prototype, the members of a secure context, the Page's context being one as about:blank's is, and those behind a feature that a context could turn on, which a Page has as its set says, since it has no origin trials. Each document that a Page loads gets a context made for it, so one at a URL that is not potentially trustworthy, such as `http://www.example.test/`, has none of the members of a secure context.
- An interface whose class has an indexed or a named property getter, such as `PluginArray`, makes Web IDL's legacy platform objects: V8 asks interceptors on its instance template for their indexed and named properties, as Blink's do ([`indexed_and_named_properties.h`](../native/bindings/indexed_and_named_properties.h)). So `navigator.plugins[0]` and `navigator.plugins["PDF Viewer"]` are own properties, read-only, the named ones not enumerable under `[LegacyUnenumerableNamedProperties]`, and listed after the indices. A named property never hides a property of the object or its prototypes, but under `[LegacyOverrideBuiltIns]`, as `DOMStringMap`'s hide even `toString`. Setting, defining or deleting one fails as Web IDL says, quietly in sloppy code and with Chrome's error in strict code, such as "Failed to set an indexed property [0] on 'PluginArray': Indexed property setter is not supported.", unless the class has a property setter or deleter: then setting or defining such a property calls the setter, which throws "Accessor properties are not allowed." for an accessor, and an index has a writable property, as `SVGNumberList`'s do; deleting a named one calls the deleter, as `bind_gen`'s interceptors do. An indexed getter that may throw, such as `SVGNumberList`'s `getItem()`, is called only below the length, so an index past the end gives `undefined`, as in Chrome. The prototype's `@@iterator` is `%Array.prototype.values%`. The generator refuses, by name, an indexed setter without an indexed getter, a named setter or deleter without a named getter, and the named properties of a global object, until a class needs them.
- The bindings of a class cannot pass it an object of an interface without a class, so a union in a member with behaviour loses such members, and an overload that needs one is never chosen: `(DOMString or TrustedScript)` converts as `DOMString` does, and `setAttribute()` has one overload. Overloads that differ in how many arguments they take are chosen by that number. A Known Gap converts to such an object as to any other.
- An error's message is the error itself, such as "1 argument required, but only 0 present.". As in Chrome, the context of the call goes in front of it as it leaves the call, through V8's exception propagation callback ([`exception_context.h`](../native/bindings/exception_context.h)): "Failed to execute 'addEventListener' on 'EventTarget': ", and for each dictionary being converted, "Failed to read the 'signal' property from 'AddEventListenerOptions': ". V8 calls it for an error thrown directly in the call, so an error that V8 throws there, such as converting a Symbol to a string, gets the context too, and one that a page's own getter throws does not.

### Runtime-enabled features

Blink puts many interfaces and members behind runtime-enabled features, which [`runtime_enabled_features.json5`](https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/platform/runtime_enabled_features.json5) lists. A Page has a set of features when it starts, and installs what is behind each one when it builds its templates, as Blink does, so that a Persona of an older Chrome Release gives it the set of its release ([ADR-0008](adr/0008-v8-and-bindings-from-web-idl.md)).

By default a Page has the Engine Release's set for stable on Windows, which the generator works out from that file as Blink's build and Chrome's startup work it out ([`runtime_features.py`](../native/bindings/bindings_generator/runtime_features.py)): a feature is on if its status for Windows is `stable`, or if the base feature that Chrome copies into it is on by default. When a page's binding asks, a feature that it depends on and that is off turns it off, and one that implies it and is on turns it on. Field trials come from the Persona, below. What Chrome's own code turns on beside the file is not counted, and the [Parity Checks of the Script Fingerprint](parity.md#the-script-fingerprint) show where that differs, but for what Chrome's content layer or Chrome itself sets when a renderer starts, where a page shows it: `LocalNetworkAccessPermissionPolicy`, from `kLocalNetworkAccessChecks`, which gives `Request` its `targetAddressSpace`, `PaymentRequest` and `PaymentApp`, from `kWebPayments` and `kServiceWorkerPaymentApps`, which expose `PaymentRequest` and `PaymentManager` with what goes with them, `SerialPortConnected`, from `device::features::kSerialPortConnected`, which gives `SerialPort` its `connected`, `TranslateService`, which Chrome's default preferences turn on and `HrefTranslate` depends on, for the `hrefTranslate` of `HTMLAnchorElement`, `WebShare`, which Chrome turns on on Windows, for `navigator.share()` and `canShare()`, and `LegacyAbstractRange`, which the content layer turns off as the inverse of `OpaqueRange`, so that `AbstractRange.prototype` has no `startContainer`.

A Page that the library starts turns on and then off the features that the `features` of its [start message](#the-messages) name, which come from its Persona: so a Page of an older Chrome Release lacks what that release did not ship yet, and each Persona's Page has what its variations seed switches, as [persona.md](persona.md#what-a-page-of-each-persona-turns-on-and-off) says. The same `features` give the V8 flags that the Page sets after the Engine Release's, before V8 starts.

Given a script, the Page program takes Chrome's options for the set instead, before the script: `--enable-blink-features=A,B` and `--disable-blink-features=C`, each a list of names separated by commas, which turn those features on and then off, so a feature that both name ends up off, as in Chrome. It refuses a name that is not a feature, and either option with `--session=`.

```text
$ out/runtime/mitto_page "'hasUAVisualTransition' in PopStateEvent.prototype"
true
$ out/runtime/mitto_page --disable-blink-features=HasUAVisualTransition "'hasUAVisualTransition' in PopStateEvent.prototype"
false
```

### Add an interface

An interface that Chrome exposes is on a Page already, from its table, with every member a Known Gap, so that its shape is Chrome's. A new Engine Release's interface gets a table with no change here, unless it uses a construct, a type or an extended attribute that the generator does not know, which stops the build with its name. To give an interface behaviour, give it a C++ class, which takes the place of its table:

1. Write its class in `native/dom/<file>.h` and `.cc`, where `<file>` is the interface's name in lowercase words, such as `pop_state_event` for `PopStateEvent`, or in a header that holds several classes, which its entry's `header` names, as `svg_elements.h` holds the classes of SVG that have nothing of their own yet: `mitto::<interface>`, which derives from `bindings::ScriptWrappable`, or from its parent interface's class, and returns its generated `bindings::V8<interface>::kWrapperTypeInfo` from `GetWrapperTypeInfo()`. It has a static `Create()` with the constructor's arguments, if the interface has one, and a method for each member, named after the member, or after its `[ImplementedAs]`, with its first letter in upper case: `Type()` for an attribute `type`, `SetCancelBubble()` for its setter, and `InitEvent()` for an operation `initEvent`. A method takes the arguments of the IDL, converted: `bool`, `const std::u16string&` for a `DOMString`, a pointer to the class of an interface, a generated struct for a dictionary, `std::optional` for an optional argument without a default. One whose member is `[RaisesException]` takes a `bindings::ExceptionState&` last. A class with an indexed property getter also has `Length()`, whose supported property indices are those below it, and one with a named property getter has `NamedPropertyEnumerator()`, its supported property names in order, and `NamedPropertyQuery()`, whether a name is one, as Blink's classes have. A getter that finds nothing returns null, or an empty `std::optional` for a `DOMString`. A named property setter takes the name and the converted value, and a deleter the name, returning whether it deleted the property; one without an identifier is `AnonymousNamedSetter()` or `AnonymousNamedDeleter()`, as in Blink. The generator writes the interceptors that call them. A static attribute is a static method; with `[SaveSameObject]` the bindings keep what it gives first on the interface object, as Chrome's keep `PerformanceObserver.supportedEntryTypes`. A class whose read-only maplike or setlike declaration has behaviour has `MaplikeEntries()` or `SetlikeValues()`, its entries in order, from which the generator writes `size`, `get()`, `has()`, `forEach()` and the iterators of `entries()`, `keys()` and `values()`. A getter may return null for an interface type that the IDL does not make nullable, as Blink's classes do. A `[LegacyFactoryFunction]`, such as `Image`, that the entry names by its name has its behaviour in the class's static `CreateForJSConstructor()`, which takes its arguments. A stringifier attribute's `toString()` gives what its getter gives, and the setter of a `[PutForwards]` attribute sets the attribute it names on what the getter gives, through V8, so that a page's own getters run, as `bind_gen`'s do.
2. Add it to `mitto_bindings_interfaces` in [`native/bindings/interfaces.gni`](../native/bindings/interfaces.gni), with the members whose behaviour it does not have yet in `missing`, or those it has in `implemented`, where `indexed getter` and `named getter` name those operations, and `maplike` or `setlike` the declaration, and its files to [`native/dom/BUILD.gn`](../native/dom/BUILD.gn). Its parent interface needs a class first. Mark it `made_by_known_gaps = true`, and give the class a static `CreateForKnownGap(info)`, which `bindings::MakeForKnownGap()` helps write, so that the Known Gaps that give its objects keep giving them ([What a Known Gap does](#what-a-known-gap-does)): otherwise the generator refuses them. Its constructor is then a member named `constructor`, which may stay a Known Gap that makes the object that way, as `new CustomElementRegistry()` does.
3. Build the Runtime. If the C++ writer refuses a type, an extended attribute or a construct that the interface uses, teach it in `cpp_types.py` or `cpp_writer.py`, following `bind_gen` for what a page sees.
4. Run the [Parity Checks of the Script Fingerprint](parity.md#the-script-fingerprint) and write their list again: a class keeps its interface's shape, so it adds no gap of the kind `shape`, and the gaps of its behaviour that it closes leave the list. Add a case of what it does to [`tests/page_cases.js`](../tests/page_cases.js), with what the Engine Release's Chrome gives for it in [`tests/data/page_cases.json`](../tests/data/page_cases.json), or a test of its own, and run the tests.

## The document

A Page's scripts get a DOM of the Runtime's own, in [`native/dom`](../native/dom), whose classes follow Blink's, with Blink's checks and messages, and whose bindings the generator writes. Its nodes live on V8's C++ heap, as Blink's do on Oilpan: a node holds its parent, children and siblings with members on that heap, and its wrapper holds it through V8's wrapping, so a node and its wrapper live and die together, a detached tree lives as long as a script holds any of its nodes, and what a script put on a node's wrapper stays while the node lives.

### The window

The global object is a `Window`, made from `Window`'s template as Blink makes a window's context, so `window`, `self` and `globalThis` are the global proxy, its prototype chain is Chrome's, `Window.prototype`, then `WindowProperties` and `EventTarget.prototype`, and each is an immutable prototype, as Web IDL has it. `window`, `self` and `document` have their behaviour, and so do `navigator`, `screen`, the window's place and size below, and what [a top-level page reads](#what-a-top-level-page-reads) of its window and document. `Window`'s other members are Known Gaps, and so is the named getter of `WindowProperties`, which would find elements by name.

What a page reads of the browser and the machine is what its Session sends, worked out by the same code or from the same data ([persona.md](persona.md#the-runtime)):

| `document.images`, `embeds`, `plugins`, `links`, `forms`, `scripts`, `anchors`, `applets`, `all`, `children`, `childNodes`, and a node's `children` and `childNodes` | Live collections of the document's tree, each the same object on every read, `plugins` being `embeds` and `applets` always empty, as in Chrome. `document.all` is undetectable, as in Chrome, and its named properties, `namedItem()`, `item()` and its call find elements by ID and by name, as [Collections](#collections) says |

`mitto::NewPageContext()` makes such a context, and the Page program makes one for about:blank and one for each document that its Session loads. The window's timers, animation frame callbacks, `queueMicrotask()`, `performance`, `fetch()` and `matchMedia()` have their behaviour, as [the event loop](#the-event-loop), [Animation frames](#animation-frames), [fetch()](#fetch) and [Media queries](#media-queries) say.

### Loading a document

Opening a Page with a URL navigates it, in [`native/page/document_loader.cc`](../native/page/document_loader.cc) on the Page's side and [`native/page_host.cc`](../native/page_host.cc) on the Session's, with the document's parser in [`native/dom/document_parser.cc`](../native/dom/document_parser.cc), as Blink's `HTMLDocumentParser` and `HTMLParserScriptRunner` have it. Everything that touches the network and cookies goes through the Session, as [ADR-0009](adr/0009-a-process-for-each-page.md) says:

- **What each Request Kind sends** is the Session's. Python gives the native Page what its Persona says a request of each kind sends, its header lines, priority and fetch parameters, when the Page opens. The library starts each of the Page's requests from that, with the same `RequestJob` and rules as a request of the C API's. So a Page's navigation sends what `session.get(url)` sends, and its script what `session.get(src, kind="script", initiator=url)` sends. A Page's requests run no timers, as Chrome's have none.
- **The Initiator** of a Page's request is its document, as the library loaded it: the URL that its navigation ended at, after redirects. The Page names the document by its ID ([The documents of a Page](#the-documents-of-a-page)), the Kind, the URL and, for `fetch()`, what the script gives, but never an Initiator, so a Page cannot claim another site's Initiator to get that site's cookies, as Chrome's network service does not take a renderer's word for it. A Page at about:blank has no Initiator to give, so its requests fail with `ERR_ACCESS_DENIED`. A URL that is not HTTP or HTTPS fails with `ERR_UNKNOWN_URL_SCHEME`, and the Page goes on.
- **The navigation** is a request of Kind `navigation` with no Initiator. The library follows its redirects, as it does a request's, and sends the Page the final response, whose URL is the document's. A navigation that fails before a response leaves the Page at about:blank, and so does a response that Chrome makes no document of, a 204, a 205 or a download, as [Navigations a page starts](#navigations-a-page-starts) says of each navigation.
- **The document** gets a new context, as Blink makes a new window for a tab's first navigation, whose about:blank has an opaque origin. Calls that wait for a promise of the old context fail, as DevTools says: `Execution context was destroyed.` The body is decoded as it arrives, in pieces of up to 64 KiB, and fed to the parser, with the encoding that Chrome works out for it, as [Text encodings](#text-encodings) says. Documents of other types than HTML are a Known Gap, which the parser reads as HTML, though they decode as Chrome decodes them.
- **Scripts** run as the HTML Standard prepares them and Blink's `ScriptLoader` and `HTMLParserScriptRunner` schedule them ([`script_loader.h`](../native/dom/script_loader.h), [`pending_script.h`](../native/dom/pending_script.h), [`document_script_runner.h`](../native/dom/document_script_runner.h)), in the orders that Chrome gave for the pages of [`tests/test_page_scripts.py`](../tests/test_page_scripts.py). The parser takes the body from tasks of the networking task source, and yields once it has parsed for 10 milliseconds since the body began, and for 500 after six such yields, as Chrome's does, though it looks at the clock only after each script and each piece of the body. An inline classic script runs as soon as the parser reaches its end tag. One with `src` is fetched through the Session as Kind `script`, with the URL resolved against the document's base URL, and the parser waits for it while other tasks run, such as scripts that the caller evaluates. What arrives of the document meanwhile waits, and the Session gets no credit for it until the parser takes it. Once the script is ready, it runs from a task of a very high priority, before the timers that wait, and the parser goes on from a later task, after the timers that the script set. One with `defer` runs after parsing, in document order, each from a task of its own at that priority. One with `async` runs from a task of the networking task source as soon as it is ready, before or after `DOMContentLoaded`, and one of another site within 3 seconds of the document's start runs at a low priority, after the tasks that wait or a second later at the latest, on a Machine of 4 GiB or more, as Chrome runs such a script while a page loads. A fetched script decodes as Chrome decodes it: with the encoding that its response's `charset` names, or else its element's `charset` attribute, taken as it is, with no white space trimmed, or else, if the attribute names no encoding, its document's encoding, as the HTML Standard has it and Chrome's preload scanner fetches a script that the parser reaches, but for a byte order mark, which wins. The query of a script's `src` is in the document's encoding, as [Text encodings](#text-encodings) says.
- **Scripts that the DOM inserts** run too. An inline one runs at once, when it becomes connected, when something is inserted into it while it is connected, or when it gets a `src` then; one with `src` runs as soon as it is ready, unless a script set its `async` to false, which makes it run in order with the others like it. Each async and in-order script holds `load` back until it has run. A script runs once: one that has run, a copy of it and one that `innerHTML` makes never run, and neither does one that has gone to another document before it runs. The first of the scripts that one call inserts runs once all of them are connected.
- **What runs**: a script whose type is a JavaScript MIME type, empty, or missing with a `language` that makes one, without `nomodule`, and with `event` and `for` only for `for="window"` and `event="onload"`. A data block does not run and fires no event. Module scripts, import maps, speculation rules and web bundles are Known Gaps. A fetched script runs if its response has an ok status, its body matches `integrity` as Blink checks it, and its MIME type is one that Chrome runs as a script, and then `load` fires at its element. Otherwise, or when it cannot be fetched, `error` fires there, and from a task of the DOM manipulation task source for a `src` that is empty or no URL. As in Chrome, a response with `X-Content-Type-Options: nosniff` whose type is no JavaScript type, and an image, audio, video or CSV one, does not run, and neither does one whose digest does not match or that came from another origin without CORS, with Chrome's console errors that say why. The console says the errors of Subresource Integrity once for each script, where Chrome says one again for each script that reuses a response from its memory cache, and checks a signed response as if it were not signed: a Known Gap. What a script leaves uncaught reaches the Session as an uncaught error, with its errors muted if it came from another origin without CORS.
- **`document.currentScript`** is the element whose classic script runs, while the microtasks that it queued run too, and null elsewhere, such as in a timer, a listener or a script's `load` event.
- **`crossorigin`, `referrerpolicy` and `fetchpriority`** change a classic script's request, as Blink's `ScriptLoader` reads them: with `crossorigin`, it goes in mode `cors`, with credentials only for `use-credentials`, in any case, and its response has to pass the CORS check, so a script of another origin that fails it does not run; `referrerpolicy` sets its referrer policy; and its priority is Blink's: `LOWEST` for an async, deferred or script-inserted script, which `fetchpriority="high"` or blocking rendering raises to the Kind's own, and the Kind's own for any other, which `fetchpriority="low"` lowers to `LOWEST`.
- **`<base>`**: the document's base URL is the `href` of its first `base` element that has one, in tree order, resolved against the document's URL, as Blink's `Document::ProcessBaseElement()` has it, and a script's `src`, a reflected `[URL]` attribute and `baseURI` resolve against it, through `Document::CompleteUrl()`, with the query in the document's encoding, while `fetch()` and `Request` parse against it with the query in UTF-8, as Blink's `KURL(base_url, input)` does. An `href` that is no URL leaves the document with none, so `baseURI` is about:blank and only absolute URLs resolve, and one of `data:` or `javascript:`, or in a document without a window, gives the document's URL, the first with Chrome's console error. A base element's own `href` resolves against the document's URL.
- **`document.cookie`** reads and writes the Session's cookies for the document's URL, as Chrome's `RestrictedCookieManager` does for a top-level page's script: a read gives no `HttpOnly` cookie, a cookie that a script sets is stored as one set by script, with `source_type` `"script"`, and a script cannot set an `HttpOnly` one. A read waits for the Session's answer, as Blink's does. A document that the Session did not load over HTTP or HTTPS, such as about:blank, has an opaque origin, so its `cookie` throws a `SecurityError`, as in a new tab of Chrome. The Page never sees an `HttpOnly` cookie's value: the response headers that it gets have no `Set-Cookie`.
- **`document.write()` and `writeln()`** insert markup at the parser's insertion point, which is just after the end tag of a script that the parser runs while the script runs, and parse it at once, as Blink's `HTMLDocumentParser::insert()` does: an inline script in it runs before the write returns, and a script with `src` in it blocks the parser once the scripts around it are done, so that what follows it, written or not, waits for it. What a script writes in pieces joins up: a tag, an attribute or a character reference may end in a later write, and an element that one leaves open takes the network's markup that follows. `writeln()` adds a line feed, each argument becomes a string and they join, and a `TrustedHTML` is its string, as no policy checks it. The errors of an inline script that a script wrote count from its start, and those of the document's scripts from where they are in its markup, as written markup does not count in positions, as in Blink. Writes nested deeper than 21 do nothing, and those within them neither until they have unwound, as Blink's `kCMaxWriteRecursionDepth` has it. With no insertion point, a write opens the document first: a script with `src` that runs async or deferred cannot, so its write does nothing and the console says Chrome's warning, `Failed to execute 'write' on 'Document': It isn't possible to write into a document from an asynchronously-loaded external script unless it is explicitly opened.`, while a write from a timer, a listener or the caller's script opens it, while it loads too. A script of another site with `src` and neither `async` nor `defer` that a write inserts gets Chrome's warning of its intervention ([`document_write_intervention.h`](../native/dom/document_write_intervention.h)), `A parser-blocking, cross site (i.e. different eTLD+1) script, ... is invoked via document.write. ...`, once as it is fetched and once more if the write leaves the parser waiting, as Blink's preload scanner of what was written finds it again. Chrome blocks such a script only on a 2G cellular connection, which a desktop never reports, so the Page fetches and runs it as Chrome on Windows does, whatever `navigator.connection.effectiveType` says.
- **`document.open()`** does nothing from a script that the parser runs, and otherwise opens the document anew, as Blink's `Document::open()`: every listener and event handler of its nodes and of its window goes, its children go, and it is loading again, in no-quirks mode until a parser finds no doctype, with a script-created parser that parses what is written at once. The parser that loaded it stops for good: a script that it waited for never runs, and what comes of the body goes unread. The document keeps its URL and its history entry, as it has its window's own. `close()` ends the input of a script-created parser, and does nothing for any other, and the document then goes through the end again: `interactive`, `DOMContentLoaded`, `complete` and the window's `load`, for the listeners added since, each before `close()` returns, and the Session hears of each `load`. A document without a window, such as one of `createHTMLDocument()`, is written and opened the same way, but runs no script. A navigation that the page started and that waits for its response stops, with the document's loading, as Blink's `FrameLoader::StopAllLoaders()` has it, so the page stays, opened; one started while the document still loads has already stopped its parser, so `open()` and `write()` then do nothing, as in Chrome. In a `beforeunload`, `pagehide`, `visibilitychange` or `unload` listener of a navigation, `open()` and a write with no insertion point do nothing, as the HTML Standard's ignore-opens-during-unload counter has it. A document that is not an HTML document throws Chrome's `InvalidStateError` for each of the four. The unload of frames and the counter that custom elements raise come with those, in later tickets.
- **Readiness**: `document.readyState` is `loading` while the parser runs, and `interactive` once it has taken all of the body, with `readystatechange`. Then the deferred scripts run, and `DOMContentLoaded` fires at the document in the task of the last, as Blink dispatches it, then a microtask checkpoint, and once no async or in-order script holds it back, `complete`, with `readystatechange`, and `load` at the window with the document as its target, in that task too, or in a task of the DOM manipulation task source once the last script that held it back has run, as Blink's `Document::CheckCompleted()` has it. When the whole body has come while the parser waits for a script, the end begins from a later task than the one that parses the rest, after the timers that the rest set, as Blink's `HTMLDocumentParser::EndIfDelayed()` has it. Nothing else that a document loads holds `load` back yet. Each of these events goes through the tree as [Events](#events) says: `DOMContentLoaded` bubbles from the document to the window, and the window's capturing listeners hear `readystatechange` and a script's `load` and `error` too.

### Navigations a page starts

A document navigates its Page's frame as Chrome 157 does, in [`native/dom/frame_loader.cc`](../native/dom/frame_loader.cc), a port of Blink's `LocalFrame::Navigate()` and `FrameLoader::StartNavigation()`, and [`native/page/page_frame.cc`](../native/page/page_frame.cc), which holds the loader of the frame's document and that of the navigation that waits for its response:

- **What starts one.** `location`'s `href` setter, `assign()` and `replace()` resolve their URL against the document's base URL, and throw Blink's `SyntaxError`, such as `'http://[/' is not a valid URL.`, with what Blink's URL parser made of it, for one that does not resolve. Its other setters change a part of the document's URL as Blink's `KURL` does, `protocol` with Blink's `'…' is an invalid protocol.`, and a `hash` that is the fragment the URL has navigates nowhere. `reload()` navigates to the document's URL again, and nothing for a `javascript:` one. A link navigates when a click that nothing canceled or handled activates it, as `click()` does, to its `href` resolved against its document's base URL: its `target`, or that of the first `base` element that has one, names the frame for `_self`, `_top`, `_parent` and none, and any other name, `_blank` among them, a new window, which Chrome's pop-up blocker opens only on a click that the user made, so nothing navigates. A Page has no user activation, so no navigation sends `Sec-Fetch-User`.
- **Refresh.** A `Refresh` header of the document's response, when the document commits, and a `meta` element whose `http-equiv` is `refresh`, once it is in the document and again whenever its `content` or `http-equiv` changes there, ask for a refresh, as Blink's `HttpRefreshScheduler` has it ([`native/dom/http_refresh_scheduler.cc`](../native/dom/http_refresh_scheduler.cc)): a delay of digits and full stops, floored to whole seconds, then, after white space or one comma or semicolon, a URL that may follow `url=` and stand in quotes, resolved against the document's base URL, and the document's own URL for none. Content with no delay asks for nothing, and so does a delay longer than 2,147,483 seconds. Of several, the one of the shortest delay wins, and the newest of equal ones. The delay starts once the document's `load` event has finished, and the navigation starts from a task of the loading task source: a reload for the document's own URL, which validates the cache, one within the document for its URL with another fragment, a replace for a delay of at most a second, and a new entry otherwise. A navigation that stops the document's loading drops its refresh. A refresh to a `javascript:` URL is refused with Chrome's console error, such as `Refused to refresh https://example.com/ to a javascript: URL`.
- **`window.open()`.** A target of `_self`, `_top` or `_parent` navigates the Page's frame, unless the URL is empty, and gives the window back, also with `noopener`; with `noreferrer` it still sends the document's `Referer`, where Chrome sends none, a Known Gap until a navigation can say its referrer policy ([#282](https://github.com/darionxt/mitto/issues/282)). Any other target, an empty one and `_blank` among them, asks for a new window, which Chrome's pop-up blocker refuses without the user's activation, so `open()` gives `null`, with nothing in the console, as in Chrome. A URL that does not resolve throws Blink's `SyntaxError`, such as `Unable to open a window with invalid URL 'http://[/'.`, with the line feed that Blink ends it with.
- **Which entry.** As Blink decides it for the session history and the Navigation API: a navigation to the document's own URL, one of the initial about:blank, `replace()`, and one that a script starts before the document's `load` event, but for a link, replace the current entry, and `reload()` reloads. `history` keeps no entries yet ([`history`](#what-a-top-level-page-reads)), but the Navigation API does, as below. More than 200 navigations in 10 seconds are dropped, with Chrome's warning in the console for the first.
- **Within the document.** A navigation to a URL that differs from the document's only in its fragment commits at once, with no request: the document takes the URL, the Session hears of it, `popstate` fires at the window with a null state, and then `hashchange`, from a task of the DOM manipulation task source, if the fragment changed, with `oldURL` and `newURL`.
- **`javascript:` and `data:` URLs.** A `javascript:` URL's text after the scheme, its escapes decoded as UTF-8, runs as a classic script from a task of the networking task source, and navigates nowhere. A string that it gives would take the document's place in Chrome: a Known Gap. A `data:` URL whose type Chrome shows is refused with Chrome's console error, such as `Not allowed to navigate top frame to data URL: data:,x`, and one of another type, which would be a download, starts nothing.
- **Before the request.** In the call that starts it, as in Chrome, `beforeunload` fires at the window, a `BeforeUnloadEvent` with the document as its target, if the document has a body. A listener that cancels it, or gives it a `returnValue`, or an `onbeforeunload` handler that returns something but null or undefined, would ask the user to stay, which Chrome does only on a page that the user has activated: the console says ``Blocked attempt to show a 'beforeunload' confirmation panel for a frame that never had a user gesture since its load. https://www.chromestatus.com/feature/5082396709879808``, and the navigation goes on. Then a document that still loads stops: its parser stops where it is, the scripts that it would run do not, the document is `complete`, with `readystatechange`, and its `load` event never fires. No navigation starts while `beforeunload`, `pagehide` or `unload` is dispatched.
- **The request** goes to the Session as a request of Kind `navigation` whose Initiator is the document, from the Persona's lines for a navigation, so it sends what `session.get(url, kind="navigation", initiator=document_url)` sends, but `Sec-Fetch-User`, with the document's URL as `Referer` under Chrome's default referrer policy. A reload validates what the cache holds, so //net sends `Cache-Control: max-age=0` when it goes to the network, and its `Referer` is the document's own URL, as for a client redirect. A navigation the same as the one that waits, started less than 3 seconds after it while no script wrote `document.cookie`, is dropped, as content's `RenderFrameImpl` drops it; otherwise a new one takes the place of the one that waits, which ends with `ERR_ABORTED`. The document goes on meanwhile, with its timers and fetches.
- **The response.** A 204, a 205 and a download, a response that `Content-Disposition` says is an attachment or whose MIME type Chrome does not show as `blink::IsSupportedMimeType()` says ([`native/mime_types.cc`](../native/mime_types.cc)), end the navigation with `ERR_ABORTED`, and the document stays, though what happened when it started does not come undone: `beforeunload` fired, and the parser of a document that loaded stopped. The library reads a download's body to its end and drops it, as Chrome's download manager reads it. A navigation that fails before a response keeps the document too, where Chrome commits its error page: a Known Gap. Any other response takes the document's place: the old document stops loading, then fires `pagehide` at the window, a `PageTransitionEvent` that bubbles and whose `persisted` is false, then, while the page is visible, `visibilitychange` and `webkitvisibilitychange` at the document, whose `visibilityState` is then `hidden`, and `unload` at the window, then a new context's document takes its place and loads as [Loading a document](#loading-a-document) says, with the `Referer` that its request sent last as its `referrer`, and fires `pageshow` right after its `load` event. Leaving the initial about:blank fires the same events there, but before it stops loading, as Blink's frame that has committed no navigation does. An `unload` listener is refused where the Persona's seed deprecates `unload`, as `document.featurePolicy` says, with Chrome's console error `Permissions policy violation: unload is not allowed in this document.` for each, as Chrome refuses one when the permissions policy disallows it.
- **The Navigation API**, as Blink's `NavigationApi` has it ([`native/dom/navigation.cc`](../native/dom/navigation.cc), [`native/dom/navigate_event.cc`](../native/dom/navigate_event.cc)). `navigation.navigate()` and `reload()` navigate as `location` does, with a `NavigateEvent` whose `info` and `destination.getState()` are those they were given, and give `committed` and `finished` promises, both rejected at once with Chrome's error for a URL that does not resolve, a `javascript:` URL, a state that cannot be cloned, a `push` from the initial about:blank, a detached window and a call while `beforeunload`, `pagehide` or `unload` is dispatched. Each navigation that a document starts, but for a `javascript:` URL, fires `navigate` at `navigation` first, before `beforeunload`, as a `NavigateEvent` whose `userInitiated` is false, as a Page has no user activation, and whose `sourceElement` is the link that started it. Canceling it stops the navigation, which fires `navigateerror` with an `AbortError` and rejects the promises of a `navigate()`. `intercept()`, for a URL that differs from the document's only in its path, query and fragment, as the history API allows, makes the navigation one within the document: it commits at once, with no request, then the handlers run, and the navigation ends with `navigatesuccess` once all their promises have fulfilled, or with `navigateerror` at the first that is rejected. A navigation that starts before one has ended aborts it, with its signal. Each commit within the document makes or replaces the current entry and fires `currententrychange`, and `navigation.transition` stands for an intercepted navigation until it ends. A new document keeps the entries of its origin from the document before it, as Chrome's browser gives a renderer the same-origin entries around the current one, with an `activation` of `push`, `replace` or `reload` whose `from` is the old entry: the new entry itself for a reload, and a detached one for a replace. A document of another origin starts with its own entry alone. Chrome 157 gives the entry of the document that a `navigate()` or `reload()` loads none of the state they were given, and neither does the Page. Known Gaps: `NavigationCurrentEntryChangeEvent`'s `navigationType`, a nullable enumeration that the bindings do not write yet, and its constructor; `NavigateEvent`'s constructor, whose dictionary holds a `FormData`; `NavigationPrecommitController.redirect()`; and an entry's `dispose` event. Traversal, `traverseTo()`, `back()`, `forward()` and `updateCurrentEntry()` are [#280](https://github.com/darionxt/mitto/issues/280)'s, with `history`.
- **Known Gaps**: a page at about:blank, whose origin is opaque, cannot navigate, since its request has no Initiator to give, and a navigation to about:blank or another URL that is not HTTP or HTTPS keeps the document, where Chrome makes a new one; a link's `ping` sends nothing; `referrerpolicy` and `rel=noreferrer` change no `Referer`, and neither does `window.open()`'s `noreferrer`; a link with `download` to a URL that the document can read, which Chrome downloads, starts nothing; so does a navigation to a URL longer than 2 MiB, `url::kMaxURLChars`, which Mojo does not carry, so that Chrome's browser makes it one to about:blank#blocked; and SVG's `a`, which Blink's `SVGAElement` follows on a click, follows nothing. A page's own `MouseEvent` whose button is not the left one still follows a link.
- **Navigation timing.** A reload's document has `performance.navigation.type` 1 and its navigation entry's `type` is `reload`, and a document of the origin of the one before it gets that document's unload times, `unloadEventStart` and `unloadEventEnd`, as Blink's `UnloadEventTimingInfo` carries them.

### fetch()

A page's `fetch()` goes through the Session as a request of Kind `fetch`, with the document as its Initiator, on the same path as the document's scripts, in [`native/dom/fetch_loader.cc`](../native/dom/fetch_loader.cc) and [`native/page/page_fetcher.cc`](../native/page/page_fetcher.cc) on the Page's side:

- **What it sends.** `Request`'s constructor checks the URL, the method and the header lines as Blink's does, with Chrome's messages, normalizes the method and drops each forbidden request header, such as `Cookie`, as its `request` guard does. A string body adds `Content-Type: text/plain;charset=UTF-8`, and an `ArrayBuffer` or a view goes as its bytes. The library starts the request from the Persona's `fetch` lines, or from those of a fetch with a body, whose `Content-Type` stands where the Persona puts it, and the script's lines take the places of the Persona's lines of their names, with the rest after them, as a caller's `headers=` do. So `fetch(url)` from a page sends what `session.get(url, kind="fetch", initiator=page_url)` sends, and the Session's cookies go with a same-origin one.
- **What comes back.** `fetch()` settles once the response starts, with a `Response` whose status, reason phrase, URL, `redirected` and headers are the response's, never with a `Set-Cookie`, or rejects with `TypeError: Failed to fetch` when the request fails first. `text()`, `json()` and `arrayBuffer()` wait for the whole body, decode it as UTF-8 with a byte order mark dropped, and parse JSON with V8's `JSON.parse()`, so its `SyntaxError`s are Chrome's. A body that fails after the response started rejects them with `TypeError: Failed to fetch`.
- **Credit.** The body arrives in pieces of up to 64 KiB, and the Page gives the Session credit for them only once a script reads the body. So a large body that nothing reads holds the server back, as a full Mojo data pipe does in Chrome, and a `Response` that the garbage collector takes cancels the rest of its request.
- **Another origin.** A cross-origin `fetch()` has no credentials, as a page's does by default. Once any hop of a request in mode `cors` goes to another origin than the document's, a fetch's or a script's with `crossorigin`, its response tainting is cors, and each response from then on, redirects included, has to pass the CORS check in the library before the redirect is followed or any of the response goes to the Page, as Chrome's network service does: `Access-Control-Allow-Origin` must be `*` or the document's origin, or `null` once a redirect from one other origin to another has tainted the request's origin, and for a request with credentials it must name the origin, with `Access-Control-Allow-Credentials: true`. A response that fails fails the fetch. The library tells the Page the tainting, so the `Response`'s type is then `cors`, also after a redirect back to the document's origin, and its scripts read only the CORS-safelisted header names and those that `Access-Control-Expose-Headers` names, where `*` names every one for a request without credentials and only itself for one with them. A request that needs a CORS preflight, such as one with a header line that is not safelisted, goes after the library's preflight, if that allows it, and otherwise fails with `TypeError: Failed to fetch` and sends nothing more to the other origin ([persona.md](persona.md#a-cors-preflight)). One that a redirect takes to another origin waits there for a preflight, if it needs one, as in Chrome.
- **`RequestInit`'s members** that change the request go to the Session with it, as Blink's `Request` takes them: `credentials`, `"omit"`, `"same-origin"` or `"include"`, which says whether the Session's cookies go, as `credentials=` does for a caller; `mode`, where `"no-cors"` takes only a CORS-safelisted method, or throws Chrome's `TypeError`, and only the no-CORS-safelisted header lines, dropping the rest as the `request-no-cors` guard does, needs no preflight, and settles with an opaque `Response` from another origin: type `opaque`, status 0, no URL, no header lines and a null body, whose bytes stay untaken, as in a data pipe that nothing drains; `referrer`, where the empty string sends none, a URL of the document's origin is sent as the referrer, and any other, or `about:client`, leaves the document's URL, and a URL that does not parse throws Chrome's `TypeError`; `referrerPolicy`, which the library applies to the referrer as Chrome's network service does; `priority`, where `"low"` sends the request at `LOWEST` and `"high"` at the Kind's own, as Blink's `ResourceFetcher` moves a fetch's priority; and `keepalive`.
- **`keepalive`.** A keepalive fetch outlives its document: when the document goes, the Page lets the request go without cancelling it, and the Session, once the next document commits, finishes it with no client, still holding it to the CORS check, and reads and drops its response, as Chrome's `KeepAliveURLLoader` finishes one in the browser after its renderer has gone. A Page that closes lets its keepalive requests go the same way. The bodies of a document's keepalive requests in flight may hold 64 KiB in all, as Blink's `ResourceFetcher` allows, and one more fails with `TypeError: Failed to fetch` before it goes. The Session allows 2,048 keepalive requests in flight, 256 of a Page and 512 KiB of their URLs and header lines, as Chrome's network service allows them a top-level frame, and one more fails with `ERR_INSUFFICIENT_RESOURCES`.

A `HEAD` request's response has a null body, as one with a null body status does: each read gives nothing, and the body is never used.

`fetch()` follows the request's signal, which follows `RequestInit`'s `signal`, or the input `Request`'s, as Blink's does: one that has aborted rejects at once with its reason, and one that aborts later rejects the promise with its reason if no response has started, and cancels the request through the Session, as Blink's `FetchManager::Loader::Abort()` does. The `Response`'s body follows the signal too, as Blink's `BodyStreamBuffer` does: a read that waits for the body rejects with the reason, and so does each later read while `bodyUsed` stays false, unless a read had all of the body first. A null body that no script read rejects the same way, as Chrome's empty body of a `HEAD` request or a null body status does.

Known Gaps of `fetch()`: `RequestInit`'s `cache`, `redirect`, `integrity`, `targetAddressSpace`, `adAuctionHeaders`, `privateToken` and `retryOptions`, which throw when given a value other than their default, `Request`'s members beyond `method`, `url`, `headers` and `signal`, a request too large for one message, with a body of nearly 16 MiB, which fails with `TypeError: Failed to fetch`, URLs that are not HTTP or HTTPS, such as `data:`, a body's stream, `clone()`, `blob()`, `formData()` and `bytes()`, and iterating over `Headers`.

### The Cache API

`caches`, `CacheStorage` and `Cache` follow Blink's, with Chrome's checks, errors and messages, and keep their entries in the Session, which runs the Cache API as Chrome's browser does, as [#262](https://github.com/darionxt/mitto/issues/262) chose: every Page of the Session shares the caches of a storage key, as two tabs of a profile do, and another Session has caches of its own. Until frames come, a document's storage key is its origin, first party.

- **Who may.** `caches` is there in a secure context, and a document whose origin is opaque, such as about:blank, gets Chrome's `SecurityError` from it.
- **The Page's side.** [`native/dom/cache_storage.cc`](../native/dom/cache_storage.cc) and [`native/dom/cache.cc`](../native/dom/cache.cc) port Blink's `CacheStorage` and `Cache`: `put()` takes a GET of an HTTP or HTTPS URL, refuses a response with `Vary: *`, a partial one and one whose body is used, takes the response's body and sends the entry; `add()` and `addAll()` fetch each request through the window's `fetch()`, refuse a response that is not ok with `TypeError: Request failed` after a console error that says why, abort the other fetches when one fails, and send all of the entries in one batch; a match, `matchAll()`, `keys()` or `delete()` with a method other than GET settles without asking, unless it ignores the method. Each promise settles from a task of its own, on Blink's queue of miscellaneous platform APIs, once the Session has answered ([The messages](#the-messages), 40 and 41).
- **The Session's side.** [`native/cache_storage`](../native/cache_storage) ports Chrome's `CacheStorage` and `CacheStorageCache`: each cache is a `//net` disk cache of its own, its operations run as Chrome's scheduler runs them, matches and keys alongside each other and each put and delete alone, a put replaces the entry of its URL whatever its method and `Vary`, a batch that would write the same URL twice fails with `InvalidStateError: ... duplicate requests (...)`, a match follows `ignoreSearch`, `ignoreMethod`, `ignoreVary` and the stored response's `Vary`, results come in the order the entries were put, caches are listed in the order they were made, a query is capped at 10 MB without its bodies, and a deleted cache still answers through the `Cache` that a page holds until the page lets it go. What a Page sends is hostile input: the library checks each call before it acts on it.
- **Bodies.** A put's body stays in the Page until the cache writes it, and goes a megabyte at a time as the Session asks, and a matched response's body comes only once a script reads it, 64 KiB at a time as the Page gives credit, as a fetch's body does. So neither side holds more of a body for the other than a part, and a body that no script reads never leaves the Session. A response with an empty body comes back with a null body, as Chrome's does.
- **Quota.** A put needs the room its entries take, before it writes anything, within the quota that Chrome enforces for a storage key, Incognito's in memory, a third of a random 15% to 20% of the Host's memory; past it, it fails with `QuotaExceededError: Quota exceeded.`. `navigator.storage.estimate()` gives what the caches hold, with `usageDetails.caches`, and 10 GiB more ([`native/storage_quota.h`](../native/storage_quota.h)).
- **Where it is kept.** In memory, until the Session goes. A directory of the Session's own comes with `storage=`.

An opaque response, which a page gets from a `no-cors` fetch, goes in and comes back opaque, with a null body, since the Runtime keeps none of its bytes. Its padding is not there yet, and neither is the V8 code cache that a service worker's put makes. A response's `body` stream is a Known Gap, as for `fetch()`.

The tests run [`tests/cache_storage_cases.js`](../tests/cache_storage_cases.js) in a Page and compare what it gives with what Chrome 157 gave for it, in `tests/data/cache_storage_cases.json`.

### The Performance Timeline

A window's `performance` keeps the entries that Blink keeps for a top-level page, from one record of how the document loaded, its `DocumentLoadTiming` and `DocumentTiming`, which `performance.timing`, the navigation's entry and `chrome.loadTimes()` all read ([`native/dom/document_load_timing.h`](../native/dom/document_load_timing.h)). The Session sends the times of each response that //net measured, which every process of the machine shares, and the Page coarsens each with `performance.now()`'s clamper, so that all of them agree with `timeOrigin` and with each other, as in Chrome ([`native/dom/performance.cc`](../native/dom/performance.cc), [`native/page/resource_timing.cc`](../native/page/resource_timing.cc)):

- **The navigation's entry**, a `PerformanceNavigationTiming` at 0, is in the timeline from the document's start, first among those at 0, and reads the document's times as they come: its fetch, connection and response from //net, redirects, `domInteractive`, `DOMContentLoaded`, `domComplete` and `load`, and its duration, which is `loadEventEnd`. Its `type` is `navigate`, its unload times 0, as a tab's first document follows none it could read, and `activationStart`, `criticalCHRestart` and `notRestoredReasons` are 0, 0 and `null` unless the navigation restarted for Critical-CH, which Chrome makes a redirect. Redirects to another origin show as none, as for a navigation that sent no referrer, and so do they in `performance.timing` and `performance.navigation`. `confidence` is `null` until the document is interactive, and then a new object for each read, as Chrome's browser process answers once Blink tells it: `high` for a navigation once the browser has started, with Chrome's noise, at the rate 0.4994798 an answer drawn at random. Its body's sizes come once all of it has.
- **`visibility-state`**: one entry at 0, `visible`, which Blink adds when it makes a window's `Performance`.
- **An entry for each of the Page's requests**, a `PerformanceResourceTiming` named by the URL it started at, `script` for a document's script and `fetch` for `fetch()`, added when it ends, failed or cancelled too, before the script runs or the body's last read settles, as Blink's `ResourceFetcher` adds it. One that the library refused before it started gets none, as Blink fails such a fetch before it loads. The Fetch Standard's TAO check, which the library runs on each hop as Chrome's `CorsURLLoader` does, decides whether the entry shows the times of its steps, its protocol, its sizes, its `deliveryType` and its `Server-Timing` metrics. CORS decides whether it shows the status, the minimized MIME type and the content coding, so an opaque response, a script's from another origin, shows neither. `renderBlockingStatus` is `blocking` for a script that the parser waits for, or that says `blocking="render"`, as Blink decides. A response from the cache is delivered from it, with no bytes on the wire, and one that the server validated counts 300 for its headers, as Blink counts them. At most 250 wait in the buffer, or as many as `setResourceTimingBufferSize()` says; past that, `resourcetimingbufferfull` fires at `performance` from a task of its own, and what its listeners make room for joins, as the Resource Timing standard says.
- **User Timing's marks and measures**, with Blink's checks and messages, in the order of their start times. A mark's or a measure's `detail` is a structured clone of what the page gave, read back once, so the same object on each read, as [Structured clone and messaging](#structured-clone-and-messaging) says, with Chrome's `DataCloneError` for what it cannot copy, such as `HTMLDocument object could not be cloned.`. A measure may start or end at an attribute of `performance.timing`, as in Chrome.
- **`performance.timing` and `performance.navigation`**, the same objects each time. `performance.timing.toJSON()` gives its attributes in the order of Blink's hash table of them, as Chrome does, and `performance.toJSON()` gives `timeOrigin`, `timing` and `navigation`.

Each entry has the window's `navigationId`, which Blink draws from 100 to 10000 for each window. Entries of paint, input, layout shifts, long tasks and soft navigations never come, since a Page paints nothing and takes no input, and `getEntriesByType()` of one of those types gives none and warns in the console, as Chrome does. `PerformanceObserver`'s constructor, `observe()` and the rest stay Known Gaps.

### Selectors

`querySelector()`, `querySelectorAll()`, `matches()`, `closest()` and `webkitMatchesSelector()` parse their selectors with the selector parser in [`native/css`](../native/css), which reads the tokens of the CSS tokenizer there as Blink's `CSSSelectorParser` reads them, and match them with [`selector_checker.cc`](../native/dom/selector_checker.cc), which follows Blink's `SelectorChecker` in its mode for queries. So what parses is what Chrome takes: every pseudo-class and pseudo-element of Blink's tables whose runtime-enabled features the Page has, the forgiving lists of `:is()` and `:where()`, relative selectors in `:has()`, `:nth-child()` and `:nth-last-child()` with `of`, `&` as `:scope`, the namespace prefixes `*` and the empty one but no other, since there is no style sheet, Blink's limits on what may follow a pseudo-element, and its unknown `::-webkit-` pseudo-elements. An empty selector and one that is not valid throw Chrome's `SyntaxError`. A selector with a pseudo-element is valid and matches nothing. The fuzz target `css_selector_fuzzer` feeds the parser any input.

Names of HTML elements and their attributes match in any case in an HTML document, and so do SVG's and MathML's camel-cased ones there; IDs and classes do in quirks mode, and so do the values of the attributes that the HTML Standard lists, on HTML elements. The structural, logical and tree pseudo-classes match as in Chrome, and the pseudo-classes that read an element's state are answered as Chrome answers them for a document that no one has typed in, clicked or focused, from the element's tag name, attributes and tree, in [`pseudo_class_state.cc`](../native/dom/pseudo_class_state.cc): `:link` and `:any-link`, `:enabled` and `:disabled` with fieldsets, legends, optgroups and selects, `:checked` with the checkedness that an `HTMLInputElement` keeps and a select's default option, `:default`, `:indeterminate` with a checkbox's `indeterminate` and a radio group that has none checked, `:required` and `:optional`, `:read-only` and `:read-write` with `contenteditable` and `designMode`, `:placeholder-shown`, `:valid` and `:invalid` with a value that is missing, an email address or URL that is not one, a `pattern` that V8 compiles with the flag `v`, and a number or date out of its range or step, `:in-range` and `:out-of-range`, `:defined` from the name or `is` value an element was made with, as `createElement()`'s options, the parser and `cloneNode()` give it, `:open`, `:modal` for a dialog that `showModal()` opened, `:dir()` from the first strong character for `dir=auto`, and `:lang()`. What needs input, focus, a frame or media, such as `:hover`, `:focus`, `:fullscreen`, `:popover-open`, `:autofill`, `:visited` and `:state()`, never matches, as in a page without them.

Known Gaps of selectors:

- `:target` never matches: Chrome sets the target once, when parsing ends, from the URL's fragment, which a Page does not look at yet.
- `:lang()` reads the language of a document from its `content-language` metas but not from the response's `Content-Language`, which a Page does not see.
- `:valid` and `:invalid` take an email address with a domain that is not ASCII as not valid, where Blink converts the domain with UTS 46 first.
- A control's form is the one its `form` attribute names, or its nearest form ancestor, but not the one that the parser's form element pointer gives a control outside its form in misnested markup.
- Chrome focuses an element with `autofocus` at its first rendering, and `:focus` then matches it, where a Page focuses nothing.
- A control's selectedness and value are read from its attributes and tree at each match, where Chrome keeps them once it has them, as its form control classes do, so the two differ once a script changes those attributes. The form controls of [#281](https://github.com/darionxt/mitto/issues/281) keep that state. Checkedness is not among them: `HTMLInputElement` keeps it as Chrome does.

### Text encodings

`TextEncoder` and `TextDecoder` follow Blink's, with Chrome's errors, and decode with Blink's codecs, which [`native/encoding`](../native/encoding) ports: the registry of encodings and their labels, and a decoder and an encoder for UTF-8, UTF-16LE and UTF-16BE, windows-1252, x-user-defined, the CJK encodings, EUC-JP, ISO-2022-JP, Shift_JIS, EUC-KR, GBK, gb18030 and Big5, and replacement, which `TextDecoder` refuses. ICU decodes and encodes the other single-byte encodings for Blink, such as ISO-8859-2 and KOI8-R, and gives the CJK codecs their indexes, from the converters and the table of names in Chromium's ICU data, which the Page program holds whole. So a label names what it names in Chrome: each of the Encoding Standard's labels, whatever its ASCII case and the ASCII whitespace around it, and none of ICU's other names. `decode()` keeps what a stream leaves of a sequence for its next call with `stream`, drops a byte order mark of UTF-8 and UTF-16 unless `ignoreBOM`, and with `fatal` throws at the first error. It takes an `ArrayBuffer` or a view on one that is neither shared nor resizable, as Blink's `[PassAsSpan]` does. `encodeInto()` writes whole code points into a `Uint8Array` that is neither shared nor resizable. `TextDecoderStream` and `TextEncoderStream` need streams, which the Runtime lacks, and stay Known Gaps. `Response`'s `text()` and `json()` decode UTF-8, as the Fetch Standard has them, as [fetch()](#fetch) says.

A document's body decodes as Blink's `TextResourceDecoder` decodes it, in [`native/encoding/text_resource_decoder.cc`](../native/encoding/text_resource_decoder.cc), with the encoding that the first of these gives:

1. **A byte order mark** of UTF-8, UTF-16LE or UTF-16BE, whatever else says.
2. **The `charset` of the response's `Content-Type`**, as `//net` parses the header for Chrome's renderer, which the Page ports since it does not link `//net`. A charset that names no encoding counts for nothing, and a `<meta>` decides then.
3. **An XML declaration** at the very start that names an encoding, even in an HTML document, unless a `<meta>` names one too. UTF-16 without a byte order mark is known by its first bytes.
4. **The prescan for a `<meta>`**, which Blink runs on the HTML tokenizer: a `<meta charset>`, or a `<meta http-equiv="Content-Type">` whose `content` names a charset, in the head, which tags inside `<title>`, `<script>` and `<style>` do not end, or in the first 1,024 bytes after it. A `<meta>` cannot name UTF-16, which is UTF-8 there, nor x-user-defined, which is windows-1252. The prescan goes on as the body comes, so a `<meta>` in a later piece decodes what follows it, and the `<title>` that came before decodes again, as in Chrome.
5. **Chrome's detector**, Compact Encoding Detection in `third_party/ced`, run as Blink's `TextEncodingDetector` runs it, on each piece until it names an encoding, with the URL's top-level domain as its hint. It never gives UTF-8 or ISO-2022-JP for a document of the web, as in Chrome, which keeps sites labelling UTF-8: a document of UTF-8 that names no encoding decodes with the default.
6. **The default**: the encoding of the URL's top-level domain in Blink's table, such as Shift_JIS for `.jp`, or else Chrome's for the language of its user interface, `intl.charset_default`, windows-1252 for the locale `en-US` of every Persona.

A document of XML or JSON that names no encoding is UTF-8, without the detector, and a style sheet's `@charset` names its encoding. `document.characterSet`, `charset` and `inputEncoding` give the encoding as the decoder has it after each piece, UTF-8 before the first. A frame takes its parent's encoding, and a frame's detector its parent's hint, when the parent is of the same origin, as Blink's `BuildTextResourceDecoder()` has it, once a Page has frames ([#285](https://github.com/darionxt/mitto/issues/285)).

A URL that a document resolves, such as a script's `src`, has its query in the document's encoding, as the URL Standard says and Blink's `Document::CompleteURL()` does it, with each character that the encoding lacks as `%26%23` its code point `%3B`, and UTF-8 for a document of UTF-16. The path and the fragment stay UTF-8, and so does a URL that `fetch()`, `Request` and `URL` parse, as in Chrome.

### Events

A node dispatches an event through the tree, as the DOM Standard says and Blink's `EventDispatcher` does ([`event_dispatcher.h`](../native/dom/event_dispatcher.h)). Its path ([`event_path.h`](../native/dom/event_path.h)) is the node, each ancestor in turn, and for a document that has a window, the window, but for an event of type `load`, which Blink never takes to the window. The capturing listeners run from the window down, then at the target its capturing listeners and then its others, each in the order they were added, then for an event that bubbles the other listeners back up to the window. `stopPropagation()`, `cancelBubble` and `stopImmediatePropagation()` stop it as in Chrome, and a dispatch clears them, sets `eventPhase` to `NONE` and `currentTarget` to null once it is done, but for the window's `load`, which Chrome leaves at the window's target phase. `composedPath()` gives the path while a listener runs, and an event of type `load` at a node has no `target` once its dispatch is done, as in Chrome. A target that is not a node, such as an `AbortSignal` or the window itself, dispatches to its own listeners alone. Each node's tree holds the event's target as its listeners see it, which is the node that dispatches until shadow trees come, which retarget it to their host there.

Listeners of `touchstart`, `touchmove`, `wheel` and `mousewheel` on a window, a document, its root element or its body are passive unless they say `passive: false`, as Blink makes them, and `preventDefault()` in a listener that says `passive: true` cancels nothing and writes Chrome's console error, "Unable to preventDefault inside passive event listener invocation.". The Runtime's own events, such as `DOMContentLoaded`, are trusted, and `dispatchEvent()` makes an event untrusted.

`click()` fires Chrome's click of a script: a `PointerEvent` that bubbles, can be canceled and is composed, with the window as its `view` and `pointerId` -1, untrusted, and nothing at an element already in the middle of its own `click()`. A click that nothing cancels, `click()`'s or a page's `MouseEvent`, fires a trusted `DOMActivate` at its target, and then runs the activation behaviour of the activation target, as Blink's `CleanUpActivationBehavior` steps do. A checkbox and a radio button have theirs, as Blink's `CheckboxInputType` and `RadioInputType` have it ([`html_input_element.h`](../native/dom/html_input_element.h)): a click of a `MouseEvent` with the primary button turns a checkbox's checkedness over and clears its `indeterminate`, or checks a radio button and unchecks the others of its group, before the listeners run; a click that a listener cancels puts back the checkedness, the `indeterminate` flag and the radio button that was checked; and one that nothing cancels fires `input` and then `change` at a connected element whose checkedness changed, and no `DOMActivate`. Every other `input` element has activation behaviour that comes with forms, as submit buttons do, and an HTML link's navigates ([Navigations a page starts](#navigations-a-page-starts)). A link with `href`, SVG's `a` and a button have activation behaviour, as Blink's do, so a click inside one leaves a summary alone; a button submits nothing yet. The main summary of a `details` element, its first `summary` child, has its own, as Blink's `HTMLSummaryElement` has ([`html_details_element.h`](../native/dom/html_details_element.h)): the click opens or closes the details, unless it was on a form control, a label, an embed or an element with activation behaviour of its own inside the summary.

#### Errors at the window

An error that a script leaves uncaught fires an `ErrorEvent` at the window, as Blink's `V8Initializer` and `ExecutionContext` fire it ([`error_reporting.h`](../native/dom/error_reporting.h)): it does not bubble and can be canceled, its `message` is V8's, such as `Uncaught TypeError: x is not a function`, its `filename` the script's URL, or the document's for a script that the Session evaluated, its `lineno` and `colno` where it was thrown, counted from 1, and its `error` what was thrown. An inline script's place counts from the document's start, from where the parser found the script, as Blink's `ClassicScript` has it. A script of another origin fetched without CORS shows the window's listeners `Script error.`, an empty `filename`, 0 for both places and a null `error`, as Chrome's do, though the Session still hears what it threw. A listener that cancels the event, or an `onerror` that returns `true`, keeps the error from the Session. An error thrown while the window's error listeners run goes to the Session alone, after the one they ran for. `reportError()` reports its argument the same way, with the place where an error was made, or else where `reportError()` was called.

A promise rejected with no handler fires a `PromiseRejectionEvent` of type `unhandledrejection` at the window, which can be canceled, from the task that reports it, and only what no listener canceled reaches the Session. A handler that comes after that report fires `rejectionhandled` from a later task. The rejection of a script whose errors are muted fires neither, as in Chrome. The Session's scripts are compiled as DevTools compiles what it evaluates, so their errors are not muted.

#### Mutation observers

`MutationObserver` and `MutationRecord` follow Blink's ([`mutation_observer.h`](../native/dom/mutation_observer.h)). Each node holds the registrations of the observers that observe it, and each change to a node's children, attributes or data queues a record for each observer that a registration on the node, or for a subtree on an ancestor, gives an interest in it: an observer that asked for old values gets the record, and the others share one with a null `oldValue`. The changes that one operation makes to a node's children are one record while each continues where the last left off ([`child_list_mutation_scope.h`](../native/dom/child_list_mutation_scope.h)), so `replaceChildren()`, `textContent` and `innerHTML` make one each, and a node that moves first leaves its parent with a record of its own. The parser's changes make records too. The observers that have records get them in a microtask, which the first record of a delivery queues, in the order the observers were made, with the records and the observer, and the observer as `this`. A subtree observer of a node that leaves the tree keeps hearing of changes under it until its next delivery. `observe()` checks its options with Blink's messages, and `takeRecords()` and `disconnect()` work as in Chrome.

### Abort signals

`AbortController` and `AbortSignal` follow Blink's, in [`native/dom`](../native/dom). `abort()` aborts the signal with its reason, or with an `AbortError` that says "signal is aborted without reason", sets the reason of every signal that follows it, then runs the abort algorithms of the signal, in the order they were added, and fires `abort`, then does the same for each signal that follows it, as Blink's `AbortSignal::SignalAbort()` does. `AbortSignal.abort()` makes an aborted signal, and `AbortSignal.timeout()` one that a timer of the Page's event loop aborts with a `TimeoutError`, queued as `setTimeout()` queues its timers, whose timer stops when the window's document goes, as Blink cancels its task. `AbortSignal.any()` makes a signal that follows the sources of the signals it is given: those that are not themselves made by `any()`, and the sources of those that are, as Blink's composition managers link them. A source holds the signals that follow it weakly, so one that nothing reaches goes, and holds strongly one that has `abort` listeners, which Blink's `AbortSignalRegistry` keeps instead. `throwIfAborted()` throws the reason as it is, with no context in front of its message, as Blink's `OmitExceptionContextInformation` leaves it.

`addEventListener()`'s `signal` adds nothing once the signal has aborted, and otherwise adds an abort algorithm that removes the listener of that type, function and capture, as Blink's does, whichever registration that is by then, which the listener keeps while the target keeps it. The algorithm finds the function by a number that it keeps on it in a private property, which a page cannot see, so it keeps no function alive. `TaskController` gives a `TaskSignal` of the priority it is made with. Changing the priority is a Known Gap, since nothing in the Runtime runs tasks by priority yet. What a signal does to `fetch()` is in [fetch()](#fetch).

### Media queries

`matchMedia()` parses its media query list with the CSS tokenizer and the media query parser in [`native/css`](../native/css), which follow CSS Syntax as Blink's `CSSTokenizer` runs it and Blink's `MediaQueryParser`, and which M9's CSS parser takes over. The fuzz target `media_query_fuzzer` feeds them any input. The `MediaQueryList` it gives writes the list back in `media` as Chrome writes it: lower case, Chrome's spacing, numbers with at most six significant digits, math functions simplified, `not all` for a query that does not parse, and a condition of a syntax that Blink does not know, Media Queries' `<general-enclosed>`, as it was given. Which media features parse follows the Page's runtime-enabled features, as in Blink: in the stable set of Chrome 157, `inverted-colors`, `prefers-reduced-data`, `video-dynamic-range`, `display-state` and `resizable` are experimental, so they do not parse, and a query of them is unknown and never matches, whatever the machine.

`matches` is worked out on each read, as Blink's `MediaQueryEvaluator` works it out for a tab of Windows Chrome, from what the Page's start message carries of the Session's Machine and Persona and nothing else:

| Media features | From |
| --- | --- |
| `width`, `height`, `aspect-ratio`, `orientation`, and the units `vw`, `vh`, `vmin` and the rest | The viewport |
| `device-width`, `device-height`, `device-aspect-ratio` | The display, over the scale, as `screen.width` and `screen.height` are |
| `resolution`, `-webkit-device-pixel-ratio` | The scale |
| `prefers-color-scheme`, `prefers-reduced-motion`, `prefers-reduced-transparency` | The three settings |
| `forced-colors`, `prefers-contrast` | The contrast theme: `active` and `more` with any theme a Machine can have, `none` and `no-preference` without one |

## The probe

The probe records a page's **Script Fingerprint**: everything that the page's scripts can reach, and what the Persona and the Machine decide of it. It is [`tools/capture/probe.js`](../tools/capture/probe.js), and it runs unchanged in real Chrome, where [the capture kit's pages](capture.md#its-recording-cases) run it for a **Baseline** in a top-level page, in frames and in a dedicated worker, and in a Page, where a **Parity Check** [opens the same page](parity.md#the-script-fingerprint). An indirect eval of it, `(0, eval)(source)`, gives a promise of its record as JSON's text, which the Page program prints and a Page's `evaluate()` returns. [`tools/capture/probe.py`](../tools/capture/probe.py) reads it.

It follows what [#207](https://github.com/darionxt/mitto/issues/207)'s walk of Chrome 155, 156 and 157 found, and uses only what V8 has, taken before it reads anything, so that it runs to its end in a Page that has few interfaces yet and goes on running as the bindings grow. It uses no regular expression, whose matches would change `RegExp`'s legacy statics, which it reads.

### What it records

1. **The walk.** From `globalThis`, breadth first, each object that it reaches, once, under the path where it found it first, such as `navigator.userAgentData`. An object reached only as another's `[[Prototype]]` gets its path last, so that `Function.prototype` is found as that and not as `Object`'s `[[Prototype]]`. For each object, its own properties in order, with their attributes, its `[[Prototype]]`, what `Object.prototype.toString` calls it, and for a function its `name`, `length` and source text where that is not `function NAME() { [native code] }`. A function whose own properties are only its usual `length` and `name`, as nearly every method and accessor is, is written where it is found. For an object that is neither a function nor a prototype, what each getter on it and on its prototype chain up to `Object.prototype` gives on it, and for a function what its own getters give, such as `Notification.permission`. A node of the DOM other than the document is written by its `nodeName` and not entered, so that no layout runs. The walk stays in its own realm: an object whose prototype chain ends at another realm's `Object.prototype`, such as the window of a frame's parent of the same origin, is written as `["foreign", tag]` and not entered, and a node of another document, such as a frame's element in its parent, by its `nodeName`. A window of another origin has no prototype, so the walk reads the few members that it shows, as a frame of another site sees its parent.
2. **The checks.** What each function, getter and setter of a prototype, and of an object whose `[[Prototype]]` is an interface's or a class's prototype, such as the window, throws when it is called on a new plain object, and what each constructor does without `new`. A promise that such a call gives is followed to what it settles with, once the microtasks queued before have run. The members of a namespace, such as `console`, `Math` or `CSS`, and the static members of an interface belong to no kind of object, so no check calls them.
3. **The values that the Persona and the Machine decide**, beyond what the getters give: `navigator.userAgentData.getHighEntropyValues()` with every hint, `matchMedia()` with each media feature that Blink's `media_feature_names.json5` names, which keywords and integers of each match, and whether the window's and the screen's sizes and `devicePixelRatio` agree with it, the resolved options of each of `Intl`'s constructors, how many values `Intl.supportedValuesOf()` gives of each kind, the time zone through `getTimezoneOffset()` on the first of each month of 2026 and `Date`'s strings of a winter and a summer day, the state of each permission that `navigator.permissions.query()` knows, and the lists of `document.featurePolicy`. Each call it waits for has a time limit of 5 seconds. A worker has no `matchMedia()` and no permissions policy, so there the probe leaves those out, and its getters give what the Persona and the Machine decide in a worker, such as `WorkerNavigator`'s values.
4. **What the page reported** to a `ReportingObserver` while the probe ran, which shows a getter or a check that queues a report.

The record holds `format`, `objects` with one entry for each object in the order found, `values` and `reports`. The probe's opening comment says what each holds, and how values and outcomes are written. Most checks throw `TypeError: Illegal invocation`, which the record leaves out, so that only the other outcomes take room.

### What it leaves out

- **Any other call.** It calls nothing that asks a person or opens something, such as `requestPermission()`, a picker, `getUserMedia()` or `window.open()`, and nothing else that follows the machine: fonts, canvas, WebGL and audio, which M9 and M10 bring, codecs and media capabilities, voices, the keyboard's layout, the battery, devices and their availability, such as `enumerateDevices()`, Bluetooth, USB, gamepads and XR, WebAuthn's authenticators, the storage estimate, and what `chrome.loadTimes()` and `chrome.csi()` return.
- **What it does not read, with why**, each in a list in the probe. The getters `window.fence` and `navigator.webkitPersistentStorage`, and `navigator.deprecatedRunAdAuctionEnforcesKAnonymity` of Chrome 155 and 156 without the variations seed, which queue a deprecation report when read (#207). The check of `Intl.v8BreakIterator` without `new`, which V8 still answers with a break iterator, and Chrome with a deprecation report. Each of these is in the record as skipped.
- **Promises that it finds.** It never waits for one, since some never settle, such as `navigator.serviceWorker.ready`. It handles each, so that one that is rejected is not reported as rejected with no handler.
- **Other realms**, such as the window of a frame's parent, which the walk does not enter. Each frame and each worker is a Recording Case of its own, in which the probe runs.

### What changes from run to run

The times, the navigation entry's random `key` and `id`, `navigator.connection`'s `rtt` and `downlink`, which #207 found, and `performance.memory`'s figures change between two runs of one Chrome. [The Normal Form of a Script Fingerprint](capture.md#the-normal-form-of-a-script-fingerprint) hides them, with the values that the machine decides, so that two records compare equal. `script_normal_form()` in [`script_normal_form.py`](../tools/capture/script_normal_form.py) writes it, and capture.md says what it hides and why.

### Its size

In Chrome 157.0.8103.39 on the Windows machine, from a user data directory with the variations seed at an HTTPS page at `capture.test`, it reaches 2,150 objects in about 100 ms, and gives the same record twice in a row but for the values above. Its record takes about 1.3 MB as `dumps_record()` writes it, with each property, getter's value, check and value of the third step on a line of its own, so that two records differ by lines, and so does its Normal Form. That is within the 1.5 MB that a Baseline of the Script Fingerprint may take for each Chrome Release, which the owner chose on 2026-11-12, for the first Recording Case. Later Recording Cases keep only [what differs from the first](capture.md#what-a-later-case-keeps), within 50 KB for a frame and 250 KB for a worker. In a dedicated worker it reaches about 740 objects. In a Page today it reaches about 250 objects.

[`tests/test_page_probe.py`](../tests/test_page_probe.py) runs it in a Page through a Session, and in the Page program, twice each, and checks that it runs to its end, leaves nothing in the console, and gives the same Normal Form.

## From Python

Until the release that ships the Runtime, Python's Page is private: `Session._open_page(url)` returns a Page that a `with` statement closes, and `await AsyncSession._open_page(url)` an AsyncPage that an `async with` statement closes. Neither is in `mitto.__all__` or in [api.md](api.md), and the release that ships the Runtime names them `open_page()`. On a Session whose library has no Page program beside it, as in a wheel that a release made, opening a Page raises a `NativeLibraryError` that says that the Runtime is not in this build. Starting the Page's process blocks for the few milliseconds that it takes, also on the event loop of an AsyncSession.

`_open_page(url, timeout=None)` navigates the Page to `url` through the Session, as [Loading a document](#loading-a-document) says, and returns once the window's `load` event has been dispatched. `timeout` is a number of seconds for that wait. A navigation that fails raises the `RequestError` that `session.get(url)` raises for that failure, and a timeout raises `PageTimeoutError`: either closes the Page first. `about:blank` navigates nowhere, as a new tab's first document needs no request. `url` is then the document's URL, after the navigation's redirects and those that the document started before it loaded, or about:blank for a response that Chrome makes no document of, such as a 204, and it follows the navigations that the Page's documents start, as each gets its response, and those within a document. The Page's scripts run in its document's context, which has V8's built-ins, its console and the interfaces that [the bindings](#the-bindings) have so far, with [timers](#timers) and [`fetch()`](#fetch).

- `evaluate(expression, timeout=None)` runs a script and returns its result as Python's `json` reads what `JSON.stringify()` writes, with `None` for what it writes nothing for. It waits for a promise to settle, as the Page program does. `timeout` is a number of seconds, as a request's total time is.
- `console_messages` holds what the scripts wrote to the console, each with its `level` and `text`, `uncaught_errors` what a console says of each error that no script caught, and `known_gaps` the name of each Known Gap that each document reached, once for each document, for tests and debugging. Each keeps the last 1000, and fewer when their text is longer than 32 Mi characters, so that a Page that writes long messages cannot fill the caller's memory.
- `wait_for_navigation(timeout=None)` waits until the next navigation that the Page's documents started has ended, and returns a `PageNavigation`: its `url`, `status`, and whether it stayed within the document, `same_document`, or ended with no document, `kept_document`, as a 204 or a download does. Each call takes the oldest that no call has taken, so one that a script starts, which the Page has heard of once the script's call has returned, counts even if it ends before the call. One to another document ends once its document has fired its `load` event or another has taken its place. One that failed before a response, or that another took the place of, raises the `RequestError` that a request to its URL raises for that failure.
- `process_id` is the ID of the Page's process.
- `close()` ends the process and waits for it to go, which takes up to 2 seconds before a kill. An AsyncPage waits for that on a thread of its own.

A call fails with an error of `mitto._errors`, sorted by what a caller does next, as a request's are. Each is a `MittoError`, and private too:

| Error | What happened | What a caller does next |
| --- | --- | --- |
| `ScriptError` | The script threw, the promise that it gave was rejected, or its result cannot be read as JSON, such as a BigInt. The message is what a console says, such as `Uncaught TypeError: x is not a function` | Fix the script. The Page goes on |
| `PageEndedError` | The Page has ended: its process crashed, ran out of memory or was killed, broke the rules of the messages, or did not know its time zone or locale, or the Session closed. Each later call raises it again | Open another Page |
| `PageTimeoutError` | The timeout passed before the result arrived, or before the document loaded. It is a `TimeoutError` too | Wait longer, or close the Page: a script that never ends keeps it busy |
| A `RequestError` | Opening the Page: its navigation failed, as `session.get(url)` would have, such as a `ConnectError` | As for that request |

A Page that has been closed raises a `ValueError`, as a closed Session does. A Page waits for its events the way the Session's requests do. Page blocks in the native core with the GIL released, and several threads may use one Page: one of them at a time waits in the native core, and hands each the result that it waits for. Closing a Page while another thread waits ends that wait first, with `mitto_page_end_waits()`. An AsyncPage wakes when the Session's event descriptor, or its waiting thread on Windows, names the Page, and takes its events without waiting. A call takes at most 100 events before it looks for its result again, so that a Page that writes without end cannot keep it from its result or its timeout, or an AsyncPage hold up the loop. Closing the Session ends its Pages, whose calls then raise `PageEndedError`, and each still needs closing.

To run the tests of Pages against a local build, name the C test program and the Page program, which the tests copy beside the library:

```bash
export MITTO_CORE_TEST="$MITTO_WORKSPACE/chromium-<tag>/src/out/mitto/mitto_core_test"
export MITTO_PAGE_PROGRAM="$MITTO_WORKSPACE/chromium-<tag>/src/out/runtime/mitto_page"
uv run pytest tests/test_page_process.py tests/test_page_program.py
```

The tests in `tests/test_native.py` and `tests/test_page.py` that open a Page need the Page program beside the library that `MITTO_NATIVE_LIBRARY` names, as in a wheel, and skip without it.
