# The Runtime

The **Runtime** runs a **Page**'s scripts in a process of its own, on the **Engine Release**'s V8, while the Page's **Session** stays in the caller's process with its network, cookies and cache ([ADR-0009](adr/0009-a-process-for-each-page.md)). Terms in **bold** are defined in [CONTEXT.md](../CONTEXT.md). [building.md](building.md#build-the-runtime) says how the Page program is built. Until the release that ships the Runtime, the Page API is private, and a wheel that a release makes holds no Page program. [From Python](#from-python) says how the private API works.

## A Page and its process

Each Page is a process of the Page program, `mitto_page`, or `mitto_page.exe` on Windows. `mitto_page_open()` in the C API starts it from the directory that the library was loaded from, which is where a wheel puts both. Without a program there, as in a wheel that a release made, it fails with `ERR_FILE_NOT_FOUND`.

The library makes the channel first, then starts the program with its end of the channel and one argument, `--session=CHANNEL,PARENT`. `CHANNEL` names that end and `PARENT` is the ID of the process that holds the library. The program's standard input is the null device, and it shares standard output and error with the process that holds the library, so that what V8 or a sanitizer reports on a crash is not lost. It inherits nothing else:

| Host | The channel | What else the Page process inherits | The Page ends when the process that holds the library ends |
| --- | --- | --- | --- |
| macOS | One end of a socket pair, at descriptor 3 | Nothing: `posix_spawn()` closes every descriptor that it is not told to pass on | Its end of the channel reads the end of the stream. It also watches its parent with a `kqueue`, for when another process holds the library's end, such as one that the parent forked |
| Linux | One end of a socket pair, at descriptor 3 | Nothing: `//base` closes every other descriptor before it starts the program, and sets `PR_SET_NO_NEW_PRIVS` | The end of the stream, and the kernel's `PR_SET_PDEATHSIG`, which kills it when the thread that started it ends. So the library starts each Page from a thread that never ends |
| Windows | The client end of a named pipe, whose handle value the argument holds | Nothing: only that handle is in `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` | The pipe breaks. It also runs in a job object of its own, with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, which ends it when the last handle to the job closes, as when the process that holds the library ends |

On Windows the job also has `JOB_OBJECT_LIMIT_DIE_ON_UNHANDLED_EXCEPTION`, so that a crash ends the process at once rather than waiting for Windows Error Reporting, and the program starts hidden, so that a caller with no console gets no window. The named pipe has a random name under `\\.\pipe\LOCAL\`, one instance, and remote clients refused. Its end in the library is not inherited by any program, and the library opens the client end itself before it starts the Page, as Mojo's `PlatformChannel` does.

On Linux, a Page process holds about 18 MB of memory before a page loads. Besides its main thread and its I/O thread it runs V8's worker threads, one fewer than the machine has cores.

## What a Page process holds and reads

A Page process holds its end of the channel and its standard streams, and opens no file or socket of its own, so that Chromium's sandbox can hold it before the Runtime ships (roadmap, M10):

- ICU's whole data file and V8's startup snapshot are inside the program ([building.md](building.md#icus-data-and-v8s-snapshot)).
- What it would read of the machine and of its browser comes from the Session, in the start message below: everything of the Session's [Machine](persona.md#the-runtime) that a page reads, such as its time zone, processors, memory, display, work area, window and network, and what the browser tells a renderer of itself, the user agent and the values of the user agent client hints of its Persona, and the languages of its `Accept-Language`. So ICU never reads `TZ`, `/etc/localtime` or the zone files. The `start` option of `mitto_page_open()` gives them, which Python fills from the Session's Machine, Persona and settings, and the library adds what `navigator.connection` gives. The Page sets the time zone and the locale as Blink sets the time zone that its browser reads, and its `navigator`, `screen` and window give the rest ([The window](#the-window)). The start also gives the runtime-enabled features and V8 flags of the Persona's Chrome Release ([persona.md](persona.md#what-a-page-of-each-persona-turns-on-and-off)), which a renderer of Chrome gets on its command line.
- V8's random numbers come from the system's random source through `//base`, which reads no file, as in Chrome's renderers.

What it holds is checked on Linux, where a test reads `/proc/<pid>/fd` of a Page that has run a script. It finds standard input on `/dev/null`, standard output and error as the test program's, the socket at descriptor 3, and the epoll and eventfd of the program's I/O thread, which name no file.

Before its `main()`, the dynamic loader of Linux opens the shared libraries of glibc, as it does for any program. After it, `strace` shows the Page reading `/sys/devices/system/cpu/online`, for how many threads V8 starts, and `/proc/self/maps`, which glibc reads to find the main thread's stack, and opening nothing else. Chrome's renderers read the same, and the sandbox of M10 has to allow them, as Chrome's does.

## Inside the Page program

The program runs V8 on its main thread, and reads the channel on a thread of its own. A Session's Page starts V8 once its start message has come, since V8 takes its flags before it starts and each isolate's runtime-enabled features are fixed when it is made: it sets the Persona's V8 flags from the start, after those of every Page of the Engine Release, starts V8 and makes the isolate with the Persona's features. Given a script, the program starts V8 before it runs it, as before, with no flags. The I/O thread checks each message, hands scripts to the main thread in the order they came, and sends their results back. Because it reads while a script runs, the process ends as soon as the channel closes, even in the middle of a script that never ends.

Each script runs in one context, so each sees what the ones before it left there. Its result is what `JSON.stringify()` writes for it, nothing for a value that it writes nothing for, such as `undefined` or a function, and what was thrown, as `Uncaught TypeError: ...`, for a script that throws or a result that cannot be written as JSON, such as a BigInt. When V8 runs out of memory, the program ends with exit code 3, which the library reports as running out of memory.

When the result is a promise, the result of the call is what the promise settles with, as when DevTools evaluates a script and waits for its promise: what it was fulfilled with, or `Uncaught (in promise) ...` and why it was rejected. The microtasks that the script queued have run by then, so a promise that they settle has settled. One that is still pending gets a handler, the call stays in progress, and the scripts after it run meanwhile. So a later script, a timer or a response can settle it, and results come in any order. Only a promise is waited for, and not another object with a `then` method.

The console is V8's own, as in Chrome, where V8 installs `console` and Blink hears of each call through V8's inspector. So the program starts an inspector, as Blink does for each isolate, and the inspector hands it each message, with its arguments written as V8 writes them for Chrome's log, separated by spaces, and the level of the method that wrote it. The inspector also gives `console` what it gives in Chrome, such as `console.createTask()`. An error that nothing caught, in a script of the document, a timer, a microtask or an event listener, goes to the Session as a console says it, `Uncaught TypeError: ...`. The program hears of each through V8's message listener, as Blink does, or reports it itself where it calls a page's function. A promise rejected with no handler is reported as Blink reports it: the promises that a task leaves rejected are reported from a task of their own, which comes after the tasks queued before it, as `Uncaught (in promise) ...`, unless a handler has come by then, also the one that a call adds to the promise it waits for. A script's console messages and the errors that it leaves uncaught reach the Session before its result, because results wait for those reports. The window's `error` and `unhandledrejection` events, `onerror` and `reportError()` are Known Gaps until M8.

### The event loop

The main thread is the Page's event loop, a `base::SingleThreadTaskExecutor` on the real clock, with no virtual time. Every task is one of its tasks: a script or a cookie answer from the Session, each step of a document's loading, each part of a response, each timer, and V8's own tasks for the main thread, such as its garbage collector's, which the program's `v8::Platform` posts there, as gin's does for Chrome's renderers ([`page_platform.h`](../native/page/page_platform.h)). Tasks run in the order they are ready: one queue holds every task source, and a delayed task joins it once its time has come. The HTML Standard lets an event loop choose among its task sources, so this is one of the orders that it allows. Chrome's queues and priorities for each source, such as loading's, are Known Gaps until M8.

Microtasks run as Blink runs them, with V8's `kScoped` policy: once the outermost script that the Runtime runs returns, which is the HTML Standard's clean up after running a script, and in a microtask checkpoint after each task, as Blink's scheduler runs one after each task. `queueMicrotask()` queues a function on V8's microtask queue, with promise jobs. A task that settles promises from C++, such as the end of a response, runs their reactions after it, not between them.

### Timers

`setTimeout()`, `setInterval()`, `clearTimeout()` and `clearInterval()` follow the HTML Standard's timer initialisation steps as Chrome runs them, in [`native/dom/dom_timer.cc`](../native/dom/dom_timer.cc), a port of Blink's `DOMTimer`:

- A timeout less than 0 is 0, and one that does not fit a `long` wraps, as Web IDL converts it.
- A timer set from a timer whose nesting level is 5 or more waits at least 4 milliseconds, so the seventh of a chain of `setTimeout(f, 0)` is the first that does. An interval grows to 4 milliseconds once it has repeated that often. Chrome counts the nesting level up before it compares it, which comes to the same.
- There is no clamp to 1 millisecond: `setTimeout(f, 1)` runs after a `setTimeout(g, 0)` set after it, as in Chrome, and `setInterval()` has none either, since `SetIntervalWithoutClamp` is on for stable.
- A timer shorter than 32 milliseconds runs on time, and a longer one when the thread wakes up anyway soon after, as Chrome posts them.
- A string runs as a classic script. An empty string sets no timer and gives 0, as in Chrome.
- IDs start at 1 and wrap at the largest `long`, skipping those in use. A timer's arguments go to its function, with the window as `this`.
- The timers stop with their window's context, when the Page loads a document.

### Clocks

The clocks are coarsened as Chrome's are, against timing attacks, each with a secret of the process that decides where the clamped value steps to the next:

- `performance.now()` and `performance.timeOrigin` to 100 microseconds, as Blink's `TimeClamper` does for a context that is not cross-origin isolated, which a Page never is. `now()` counts from the start of the navigation that loaded the document, which the Session sends, and from when the context was made for about:blank. So `performance.now()` gives multiples of 0.1, up to the rounding of a double, such as `52.80000000074506`.
- `Date.now()` and `new Date()` read the clock that the program's `v8::Platform` gives V8, coarsened to 5 microseconds as gin's `TimeClamper` does, which shows only within 5 microseconds of a millisecond's boundary.

Given a script on its command line instead of `--session=`, the program has no Session to start it, so its `navigator` and `screen` give empty strings and zeros, and `devicePixelRatio` 1. It runs the script, then its event loop until no task is ready and no timer is set, and prints the result, which [building.md](building.md#build-the-runtime) describes: what a promise that the script returns was fulfilled with, or why it was rejected, or that it never settled. There, `fetch()` fails, for want of a Session. Either way, the context has the interfaces that the Runtime implements, as the Page's runtime-enabled features expose them ([the bindings](#the-bindings)).

## The channel

The channel is the native core's own, on `//base`, and not Chromium's Mojo ([ADR-0009](adr/0009-a-process-for-each-page.md)). In the library, the network thread reads and writes it, on its message pump: with a watch on the socket on macOS and Linux, and with overlapped reads and writes on the pipe, which complete on the thread's completion port, on Windows. The Page program does the same on its I/O thread. Neither ever blocks on it: what the system cannot take yet waits in memory.

Each message travels as a frame: the size of its payload and its type, each a 32-bit little-endian number, and then the payload. Each side refuses a frame whose payload is larger than 16 MiB, so that the other cannot make it hold more for one message. So a script can be at most 16 MiB less 8 bytes, and a result whose JSON is larger fails with a message that says so.

[`native/page_messages.h`](../native/page_messages.h) holds the frames and the messages, which both programs build. [`native/page_channel.h`](../native/page_channel.h) holds the channel, with one file for macOS and Linux and one for Windows.

## The messages

Version 7 of the messages:

| Type | Name | Way | Payload |
| --- | --- | --- | --- |
| 1 | Hello | Each way, first and once | The version of the messages that the sender speaks, a 32-bit number |
| 2 | Refused | Each way | Why the sender refuses what it got, in UTF-8. The sender closes the channel after it |
| 3 | Start | To the Page, once, after the hello | A JSON object with what the Page would otherwise read of the machine and the browser, each key of the `start` option of `mitto_page_open()`: `time_zone`, `locale`, `processors`, `touch_points`, `work_area_x`, `work_area_y`, `work_area_width`, `work_area_height`, `window_state`, `window_x`, `window_y`, `window_width`, `window_height`, `contrast_theme`, `inverted_colors`, `memory`, `screen_width`, `screen_height`, `scale`, `viewport_width`, `viewport_height`, `color_scheme`, `reduced_motion`, `reduced_transparency`, `effective_type` and `navigator`, an object of `user_agent`, `platform`, `languages` and `user_agent_data`, which `mitto.h` describes. Beside them, `connection`, which the library adds: the `rtt` in milliseconds and the `downlink` in Mbps that `navigator.connection` gives about:blank's document. And `features`, what the Page turns on and off beside the Engine Release's runtime-enabled features and V8's defaults: `enable_blink_features` and `disable_blink_features`, lists of names of runtime-enabled features, and `v8_flags`, a list of V8's flags, each as gin writes one, such as `--no-foo` |
| 4 | Evaluate | To the Page | The number of the call, a 64-bit number, and the script in UTF-8 |
| 5 | Evaluated | To the Session | The number of the call, a byte that is 0 for a result and 1 for a failure, and then the result as JSON, or why it failed, in UTF-8. Results come in any order, since a call whose result is a pending promise waits for it |
| 6 | Console | To the Session | A byte for the level, 1 to 5 for debug, log, info, warning and error, and then the message, in UTF-8 |
| 7 | Uncaught error | To the Session | What a console says of an error that no script caught, such as `Uncaught (in promise) Error: no`, in UTF-8 |
| 8 | Request | To the Session | The number of the request, a 64-bit number, larger than that of each request before it, a byte for its Request Kind, 1 for `script` and 2 for `fetch`, a byte that is 1 for a fetch of mode `same-origin`, whose hops the library keeps to the document's origin, its URL in UTF-8, its method and the header lines that the page's script set, each `name: value` and a line feed, each of these three after its size as a 32-bit number, and then a byte that is 1 if a body follows, which is the rest |
| 9 | Credit | To the Session | The number of a request, and how many more bytes of its body the Page has taken, a 32-bit number |
| 10 | Get cookies | To the Session | The number of the question, a 64-bit number |
| 11 | Set cookie | To the Session | What a script set `document.cookie` to, in UTF-8 |
| 12 | Loaded | To the Session | Nothing: the window's `load` event has been dispatched |
| 13 | Response started | To the Page | The number of the request, 0 for the navigation, its status, a 32-bit number, a byte that is 1 if it followed a redirect, a byte that is 1 if its tainting is cors, because a hop went to another origin than the document's, when the navigation started, as a 64-bit count of microseconds of `base::TimeTicks`, which every process of the machine shares, and 0 for the Page's own requests, what the document's `navigator.connection` gives, its `rtt` as a 32-bit number and its `downlink` as a 64-bit IEEE double, each 0 for the Page's own requests, then its URL and its reason phrase, each after its size as a 32-bit number, and then its header lines, each `name: value` and a line feed, but for `Set-Cookie` and `Set-Cookie2` |
| 14 | Response body | To the Page | The number of the request, and the next bytes of its body |
| 15 | Response ended | To the Page | The number of the request, and a net error, a 32-bit number: 0 when all of the body has come, and otherwise why the request failed, with or without a response |
| 16 | Cookies | To the Page | The number of the question that it answers, and the document's cookies, as a `Cookie` header's line holds them |
| 17 | Cancel | To the Session | The number of a request that the Page no longer wants. Its end follows, with `ERR_ABORTED`, unless it has ended already |

The library sends its hello, the start and any script at once, without waiting for the Page's hello, because the Page reads them in order.

A body travels only as far as the Page has given credit for it. Each request starts with 64 KiB of credit, as much as the library holds of a request's body for a caller, and the library reads more of the body from `//net` only once the Page has given credit back for what it took. So a Page that takes its bodies slowly, as a parser that waits for a script does, slows the server down, as a slow reader of a request does. The library answers questions for cookies in the order they come, and the channel keeps the order of everything, so a read of `document.cookie` after a write sees it, and so does a request that the Page asks for after it.

Both programs come from one tree and ship together, so the version on both sides must be the same, and it changes with any change to the messages. Each side refuses, with a Refused message that says why:

- a hello of another version, and any message before the hello;
- a type that it does not know, or one that only goes the other way;
- a payload that is not what its type says, such as text that is not UTF-8 or a console message of an unknown level;
- a frame larger than the channel carries;
- for the library, a result of a call that is not in progress, a request whose number is not larger than the one before, more than 2700 requests at once, as Chrome's network service allows a renderer process, credit for a request that the Page has not asked for, or for more of a body than the library sent, or a cancel of one that it has not asked for. Also a request whose method is not a token or is forbidden, such as `TRACE`, whose header lines are not valid or include a forbidden request header, such as `Cookie` or one that starts with `Sec-`, that has a body with `GET` or `HEAD`, or that asks for a script with any of these: Chrome's network service refuses such a request from a renderer too, and a Page that sends one is not the Runtime's;
- for the Page, a second start, a script before the start, a start that lacks a key or has another, or a value that a Machine, a Persona or Chrome's network estimate cannot have, a time zone or locale that ICU does not know, a name in its features that is not a runtime-enabled feature, a response whose `rtt` or `downlink` Chrome cannot give, a response or body of a request that is not in progress, more of a body than it has given credit for, or cookies for a question that no script waits for.

The library reads what a Page sends as hostile input: a Page runs a site's scripts. It checks each frame field by field before it acts on it, and the fuzz target `page_messages_fuzzer` feeds any bytes to that code ([building.md](building.md#sanitizer-builds-and-the-fuzz-target)). When the library refuses, it also kills the Page process, rather than trusting it to end.

A refusal ends the Page, and its calls fail with `MITTO_PAGE_ERROR_REFUSED` and a message that says which side refused what, such as:

```text
the library refused a message from the Page: the Page speaks version 99 of the messages, and the library speaks 1
the Page refused a message from the library: the time zone "Mars/Olympus_Mons" is unknown
```

## The C API

[`mitto.h`](../native/include/mitto/mitto.h) has the Page's calls, which return at once, and its events, which wait in a native queue as a request's do ([ADR-0003](adr/0003-c-abi-and-ctypes.md)):

- `mitto_page_open()` opens a Page on a Session, with versioned JSON options, whose `start` is what the Page starts with. An unknown key is refused. With `url`, the Page navigates there once it opens, as [Loading a document](#loading-a-document) says, with what each Request Kind sends in `requests`.
- `mitto_page_evaluate()` sends a script and stores the number of its call. Each call gets one `MITTO_PAGE_EVENT_EVALUATED` event, with the result as JSON or an error.
- `mitto_page_next_event()` takes the next event, blocking for as long as the caller says, and `mitto_page_event_free()` releases it. Beside `MITTO_PAGE_EVENT_EVALUATED` and `MITTO_PAGE_EVENT_ENDED`, a Page has a `MITTO_PAGE_EVENT_CONSOLE` event for each console message, with its level, a `MITTO_PAGE_EVENT_UNCAUGHT_ERROR` event for each error that no script caught, a `MITTO_PAGE_EVENT_NAVIGATED` event when its navigation has its response, with the document's URL and status, or has failed, with the net error, and a `MITTO_PAGE_EVENT_LOADED` event when the window's `load` event has been dispatched.
- `mitto_page_end_waits()` ends each wait of `mitto_page_next_event()` on another thread, and makes each later one return at once if no event waits, so that the thread that closes a Page can stop another that waits, as `mitto_session_end_waits()` does for a Session.
- `mitto_page_process_id()` gives the ID of the Page's process.
- `mitto_page_close()` closes the Page.

At most 1000 console messages and uncaught errors of a Page wait untaken, and at most 32 MiB of their text, so that a Page that writes without end cannot fill the memory of the process that holds the library. V8's inspector keeps as many console messages for DevTools. The library drops the ones past that, and the next one that has room comes after a console warning that says how many it dropped. Results and the end of the Page are never dropped.

A Page's events list its handle in the Session's list of what is ready, beside its requests' events. So the file descriptor that an asyncio caller watches on macOS and Linux, and `mitto_session_wait_for_event()` on Windows, wake for both. `mitto_session_next_ready()` names the handle and says whether it is a request's or a Page's.

## How a Page ends

Each way of ending reaps the process, so none is left behind:

- `mitto_page_close()` closes the channel. The Page process reads the end of the stream and ends at once. The call waits for that, for up to 2 seconds before it kills the process, and returns once the process has gone.
- `mitto_session_destroy()` does the same for each Page of the Session. Each Page gets a `MITTO_PAGE_EVENT_ENDED` event with `MITTO_PAGE_ERROR_SESSION_DESTROYED`, and its handle stays valid until it is closed.
- When the process that holds the library ends without either, the Page process ends as the table above says.
- When the Page process crashes, runs out of memory or is killed, the library reads the end of the stream on the network thread, and a worker thread reaps the process to learn how it ended. Each call in progress then fails with `MITTO_PAGE_ERROR_PROCESS_ENDED`, a `MITTO_PAGE_EVENT_ENDED` event follows, and each later call fails the same way. The message says how the process ended, such as `the Page process was ended by signal 9` or `the Page process ran out of memory`. The Session's other Pages and requests go on.

On macOS and Linux the library reaps its Page processes with `waitpid()` on the process's ID. A caller that waits for any child, or ignores `SIGCHLD`, can take a Page's exit status first. The library then says that the process ended and that something else in the process took its exit status.

## The bindings

What a page's scripts can reach of the Web's interfaces, and how, is part of its **Script Fingerprint**. So the Runtime's V8 bindings come from the Engine Release's Web IDL files, as Chrome's do, and are written by a generator of mitto's own, [`native/bindings/bindings_generator`](../native/bindings/bindings_generator), which GN runs on every build of the Runtime. Blink's own generator, `bind_gen`, writes code for Blink's classes, which mitto does not have. The generator follows `bind_gen` for everything a page can see: which properties each object has and in which order, their attributes, names and `length`s, and the errors that each call throws, with Chrome's messages. Each module names the files of Blink's that it follows on its `Upstream:` lines.

### How the generator works

It runs in four steps, all in [`native/bindings/generate_bindings.py`](../native/bindings/generate_bindings.py) and the package next to it:

1. **Read.** Blink's scripts build the [Web IDL database](building.md#the-web-idl-database) from the IDL files of every interface that Chrome exposes to pages, with their partial interfaces and mixins merged in. The generator loads it with Blink's own `web_idl` package and reads every definition into a model of its own ([`web_idl_reader.py`](../native/bindings/bindings_generator/web_idl_reader.py), [`model.py`](../native/bindings/bindings_generator/model.py)): interfaces, namespaces, dictionaries, callbacks, enumerations, and each of their members, types and extended attributes. It reads all of them, whether or not the Runtime implements them yet, and it refuses anything it does not know, with a message that names it and where it is: a kind of definition, a type, or an extended attribute that [`extended_attributes.py`](../native/bindings/bindings_generator/extended_attributes.py) does not list. That file gives each of the 73 extended attributes that the database of 157.0.8103.39 uses a role: what it changes for a page, or that only Blink's implementation reads it, such as `[Measure]`. So when an Engine Release brings a construct that nobody has looked at, the build stops with its name, instead of writing bindings that are wrong.
2. **Plan.** For every interface, [`install_plan.py`](../native/bindings/bindings_generator/install_plan.py) works out the own properties of its interface object, prototype and instances in the order that Chrome installs them. `bind_gen` installs the members that are always there on V8's templates first, then those behind a runtime-enabled feature, and later, on each context's objects, those that the context decides, such as `[SecureContext]` members. V8 adds `constructor` to the prototype between the two. Within each of these, Blink installs the attributes, then the constants, then the operations, which `web_idl` sorts by name, with the members of one condition together. `[LegacyUnforgeable]` members go on each instance, not configurable. Chrome's renderer takes the objects of `Window`, `Document`, `HTMLDocument`, `Node`, `EventTarget` and `WindowProperties` from its V8 context snapshot, which holds only the members that are always there, so for these the members behind a feature come last, on each context's objects.
3. **Write.** It writes into `out/runtime/gen/mitto/bindings` the bindings of every interface, namespace and callback interface that a Page's global object exposes, and of each ancestor of one, in one of two forms:
   - For each interface that has a C++ class in the Runtime, [`cpp_writer.py`](../native/bindings/bindings_generator/cpp_writer.py) writes `v8_<interface>.h` and `.cc`: a callback for each attribute, operation and constructor, and the function that installs them on the interface's templates in the order of the plan. It converts values as Web IDL says, in the order of `bind_gen`'s callbacks: V8's signature check of the receiver, which throws "Illegal invocation"; then for a constructor that it is called with `new`; then the number of arguments; then each argument in turn ([`cpp_types.py`](../native/bindings/bindings_generator/cpp_types.py)). It handles only the types and extended attributes that those interfaces use, and refuses any other there, naming it: adding a class may mean teaching it more.
   - For every other, [`table_writer.py`](../native/bindings/bindings_generator/table_writer.py) writes a table: its `WrapperTypeInfo` and each of its own properties in the order of the plan, with its kind, attributes, `length` and condition. [`interface_table.cc`](../native/bindings/interface_table.cc) installs a table on the construct's template, and on each context's objects for what the context decides, as `bind_gen`'s install functions do. A table holds data and no code, so the thousand or so interfaces without a class cost the Page program under 1 MB and their build a few seconds ([building.md](building.md#times-and-sizes)). The tables go into a fixed number of files, `interfaces_without_class_<n>.cc`, which [`generated_files.gni`](../native/bindings/generated_files.gni) names, so that GN knows them before the generator runs.

   It also writes the dictionaries and unions that the classes' bindings use, the table of runtime-enabled features, and the function that sets up a Page's global object. The generator writes a file only when its content changes, so a change to the generator or to `interfaces.gni` compiles again only the files it changes.
4. **List.** It writes `web_idl_listing.txt`, every interface and member that it planned, one per line, with the features and conditions each is behind. The release routine compares it between two Engine Releases ([releasing.md](releasing.md#2-check-out-the-new-engine-release)).

A page sees every interface, namespace and callback interface that Chrome exposes on `Window`, as [ADR-0008](adr/0008-v8-and-bindings-from-web-idl.md) has it, behind the features and conditions of each: 1,061 in the listing of 157.0.8103.39. Those with a C++ class are in [`native/bindings/interfaces.gni`](../native/bindings/interfaces.gni), and every member of one without a class is a Known Gap. Each class is `mitto::<interface>` in [`native/dom`](../native/dom). A member whose behaviour the Runtime lacks is a **Known Gap**: its binding is installed as Chrome's is, so the shape matches, and [What a Known Gap does](#what-a-known-gap-does) says what happens when a page calls it. An entry there either lists its Known Gaps in `missing`, as `EventTarget` does for `when()`, whose `Observable` the Runtime does not have, or lists in `implemented` the members its class has, so that every other member is a Known Gap, as the DOM's large interfaces do. `get x` there names the getter of an attribute alone. The generator gives a reflected attribute of a string or a boolean, `[Reflect]` with no URL and no list of values, its behaviour itself, through the element's content attribute, and leaves an indexed or named property operation that is a Known Gap out, so that a page reads nothing through it.

For Chromium 157.0.8103.39, the generator reads the whole database and writes everything in about 3 seconds, and the listing has 20,237 lines, about 1.2 MB.

### What a Known Gap does

A Known Gap does what the owner chose on 2026-11-12, in [#208](https://github.com/darionxt/mitto/issues/208), whose comment compares the options. Before, it threw `TypeError: Not implemented.`, which Chrome never says, so one caught error told a page that it did not run in Chrome, and the page's script stopped where Chrome's goes on. In short, it does what Chrome's binding does up to the call into Blink, tells the Session, and gives its type's default. Its callbacks are in [`known_gap.cc`](../native/bindings/known_gap.cc), the same for an interface with a class and one without, and they read the member's types and overloads from tables that the generator writes into `idl_types.cc` ([`type_tables.py`](../native/bindings/bindings_generator/type_tables.py)):

1. **Chrome's checks first.** In the order of `bind_gen`'s callbacks, with Chrome's messages, as the binding of a member with behaviour does, it:
   - checks the receiver;
   - for a constructor, checks that it is called with `new`;
   - checks the number of arguments;
   - resolves the overloads;
   - converts each argument as Web IDL says.

   For an operation that returns a promise, an error from any of these rejects the promise. So a wrong argument fails as it does in Chrome, and the page's own getters, iterators, `valueOf()` and `toString()` run as they run in Chrome. The converted arguments are thrown away: only the call into the Runtime's C++ is missing. [`idl_conversions.cc`](../native/bindings/idl_conversions.cc) converts each type as Blink's `NativeValueTraits` do, with their messages, a union as `bind_gen`'s `union.py` tries its members, and a dictionary's members in order, with the member being read in front of an error. It resolves overloads as `bind_gen`'s overload dispatcher does: the items of Web IDL's effective overload set that take as many arguments as the call gives, and among them the one that the value of the distinguishing argument selects, by the same tests in the same order. A call that no overload takes throws "N arguments required, but only M present." with the fewest that any overload needs, or else "Overload resolution failed.".
2. **A report.** It tells the Session the first time a document reaches it after its arguments have converted, named as the listing names it, such as `Navigator.prototype.getBattery`, or `new Highlight` for a constructor. The bindings remember for each document which they reported; the Page passes the report on to the Session in a later step of M7. Chrome's use counters count a feature the same way, once for each document (`UseCounterImpl::Count()` in `third_party/blink/renderer/core/frame/use_counter_impl.cc`). A Known Gap inside a member's behaviour, such as a selector that needs more than simple selectors, reports the same way. The generator also marks each Known Gap in `web_idl_listing.txt`, so that each build writes all of them down, including those that no Parity Check sees.
3. **Its type's default.**

   | Member | What it does |
   | --- | --- |
   | Getter | Gives the value that its setter last stored on that object, or else its type's default |
   | Setter | Stores the converted value for the getter |
   | Operation | Returns its return type's default, a new object for an interface |
   | Operation that returns a promise | Returns a promise resolved with the default of the promised type |
   | Constructor | Returns an object of the interface with nothing behind it |

   A type's default is:
   - `null` for a nullable type;
   - `false`, 0 or `""`;
   - an empty array for a sequence or a frozen array;
   - `undefined` for `any`;
   - the first value of an enumeration;
   - for an interface, an object of that interface with nothing behind it, whose members are Known Gaps too.

   A getter gives the same such object each time on one receiver, unless the IDL says `[NewObject]`. An iterable, maplike or setlike declaration on an object with nothing behind it iterates over nothing: its `entries()`, `keys()` and `values()` give an iterator of Chrome's shape, whose prototype holds `next()` and the iterator's name for `@@toStringTag`, such as "URLSearchParams Iterator", and inherits from V8's `%IteratorPrototype%`, or its Map, Set or async iterator prototype, and whose `next()` is done at once. The generator writes the table of each such iterator itself, since Blink's database merges them into their interfaces.

Some members follow other rules:

- **Event handler attributes** are not Known Gaps. The generator gives them Chrome's behaviour, as it does for reflected attributes. The getter gives `null` until a handler is set. The setter stores any object, and turns anything else into `null` without throwing, as `JSEventHandler::CreateOrNull()` does. The handler is a listener of its EventTarget ([`event_handlers.h`](../native/dom/event_handlers.h)): it joins the listeners the first time it is set, keeps its place when it is set again, and goes when it is set to `null`, as the HTML Standard's event handlers do. A dispatch calls it with the current target for `this` and the event for its argument, does nothing for one that cannot be called, and cancels the event when it returns `false`, as Blink's `JSEventHandler::InvokeInternal()` does. An `HTMLBodyElement`'s handlers of the window's events, such as `onload`, are its window's. A handler written in a content attribute, such as `<body onload="...">`, is not compiled yet, and neither is the special handling of an `ErrorEvent` at a window or of `beforeunload`, events that the Runtime does not fire.
- **A stringifier attribute's `toString()`**, such as `URL`'s for `href`, gives what the attribute's getter gives, the value its setter stored among it, as Blink's `toString()` is that getter.
- **An attribute's setter** ignores a string that is not one of its enumeration's values, as Web IDL says, and one with `[PutForwards]` sets the attribute it names on what the getter gives, as `bind_gen`'s setters do. A setter of a nullable type, a dictionary, `any` or an event handler called with no argument throws "1 argument required, but only 0 present.".
- **An object of an interface without a class** whose nearest ancestor with a class is `EventTarget` or `Event` has an object of that class behind it, which the DOM makes ([`objects_behind.h`](../native/dom/objects_behind.h)), so that `addEventListener()` and `dispatchEvent()` work on an `AbortSignal`, and `type` and `bubbles` on a `CustomEvent`, which its constructor's `type` and `EventInit` give. Its own members stay Known Gaps.
- **The generator refuses by name** a Known Gap whose default would be unsafe or impossible:
  - a member of `Crypto` or `SubtleCrypto`, whose default would be predictable random values or keys;
  - an attribute or operation that gives an object of an interface that has a C++ class, whose class's members would find no object behind it.

  Each of these needs behaviour, or an outcome written by hand. Until it has one, it keeps `TypeError: Not implemented.` ([`known_gaps.py`](../native/bindings/bindings_generator/known_gaps.py)), and the listing marks it "Known Gap, refused". An object that a Page has no bindings for, such as one of an interface exposed only to workers, is refused the same way. For Chromium 157.0.8103.39, 107 members are refused.
- **The members that pages call most** get behaviour, or Chrome's outcome for the Page's state, written by hand, unless the default already is Chrome's outcome. These are the members used on at least 1% of page loads, by Chrome Platform Status's use counters. Chrome's outcome is the one for a Machine that has granted no permission, has only the devices it claims, and has no user activation. For example, `navigator.permissions.query()` gives `"prompt"`, where the first value of `PermissionState` would say `"granted"`. Where Chrome waits for a person, the outcome may be a promise that never settles, as `getUserMedia()` waits at its prompt. A member written this way is no longer a Known Gap.

The defaults keep a page's script running where Chrome's runs, and with it the requests the script makes. They are often Chrome's own values too. In a walk of a new page in Chrome 157, 85% of the getters within three steps of `window` gave their type's default, every event handler among them. A Parity Check therefore shows a Known Gap only where its default differs from Chrome's value.

### What the bindings run on

The generated callbacks and tables call a small runtime in [`native/bindings`](../native/bindings), on V8's own API, as Blink's `platform/bindings`:

- A Page's global object gets each interface object, namespace object, `[LegacyWindowAlias]` and `[LegacyFactoryFunction]`, such as `Image`, as a lazy data property that is not enumerable, as Blink's `IDLMemberInstaller::InstallExposedConstructs()` installs them: V8 makes the object the first time a page reads it, and the property is a data property from then on ([`idl_member_installer.h`](../native/bindings/idl_member_installer.h)). Those that are always there go on the template of the global object, and V8 installs a template's lazy data properties before its other properties, last first, as it does in Chrome. So `Object.getOwnPropertyNames(window)` lists V8's builtins, then the interface objects from `Option`, `Image` and `Audio` back to `AbortController`, then the members of `Window`, then what the context decides, as Chrome's does.
- Each context makes an interface object once, with its parent's for its own prototype, and installs on it and its prototype what the context decides, before a wrapper of the interface or anything else can reach them, as Blink's `V8PerContextData::ConstructorForType()` does. A namespace object is made each time its property is read, which happens once.
- The Runtime's C++ objects live on V8's C++ heap, cppgc, on which Blink's Oilpan is built, so that V8 collects them with the JavaScript objects that refer to them ([`script_wrappable.h`](../native/bindings/script_wrappable.h)). A wrapper holds its object through `v8::Object::Wrap()`, with the type tag that Blink's Web IDL database gives the interface, and the object holds its wrapper through a traced reference. A listener that a page adds is held the same way, so a target, its listeners and their closures go together when nothing else holds them.
- An argument converts to an object of an interface only if V8's template of that interface, or of one that inherits from it, made it, and its tag lies in the interface's range.
- What each context decides is installed once its interface objects exist: the `@@unscopables` of a prototype, the members of a secure context, the Page's context being one as about:blank's is, and those behind a feature that a context could turn on, which a Page has as its set says, since it has no origin trials. Each document that a Page loads gets a context made for it, so one at a URL that is not potentially trustworthy, such as `http://www.example.test/`, has none of the members of a secure context.
- The bindings of a class cannot pass it an object of an interface without a class, so a union in a member with behaviour loses such members, and an overload that needs one is never chosen: `(DOMString or TrustedScript)` converts as `DOMString` does, and `setAttribute()` has one overload. Overloads that differ in how many arguments they take are chosen by that number. A Known Gap converts to such an object as to any other.
- An error's message is the error itself, such as "1 argument required, but only 0 present.". As in Chrome, the context of the call goes in front of it as it leaves the call, through V8's exception propagation callback ([`exception_context.h`](../native/bindings/exception_context.h)): "Failed to execute 'addEventListener' on 'EventTarget': ", and for each dictionary being converted, "Failed to read the 'signal' property from 'AddEventListenerOptions': ". V8 calls it for an error thrown directly in the call, so an error that V8 throws there, such as converting a Symbol to a string, gets the context too, and one that a page's own getter throws does not.

### Runtime-enabled features

Blink puts many interfaces and members behind runtime-enabled features, which [`runtime_enabled_features.json5`](https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/platform/runtime_enabled_features.json5) lists. A Page has a set of features when it starts, and installs what is behind each one when it builds its templates, as Blink does, so that a Persona of an older Chrome Release gives it the set of its release ([ADR-0008](adr/0008-v8-and-bindings-from-web-idl.md)).

By default a Page has the Engine Release's set for stable on Windows, which the generator works out from that file as Blink's build and Chrome's startup work it out ([`runtime_features.py`](../native/bindings/bindings_generator/runtime_features.py)): a feature is on if its status for Windows is `stable`, or if the base feature that Chrome copies into it is on by default. When a page's binding asks, a feature that it depends on and that is off turns it off, and one that implies it and is on turns it on. Field trials come from the Persona, below. What Chrome's own code turns on beside the file is not counted, and M7's Baselines show where that differs, but for the features that Chrome's content layer copies from a `base::Feature` of another name that is on by default, where a page shows them: `LocalNetworkAccessPermissionPolicy`, from `kLocalNetworkAccessChecks`, which gives `Request` its `targetAddressSpace`, and `PaymentRequest` and `PaymentApp`, from `kWebPayments` and `kServiceWorkerPaymentApps`, which expose `PaymentRequest` and `PaymentManager` with what goes with them.

A Page that the library starts turns on and then off the features that the `features` of its [start message](#the-messages) name, which come from its Persona: so a Page of an older Chrome Release lacks what that release did not ship yet, and each Persona's Page has what its variations seed switches, as [persona.md](persona.md#what-a-page-of-each-persona-turns-on-and-off) says. The same `features` give the V8 flags that the Page sets after the Engine Release's, before V8 starts.

Given a script, the Page program takes Chrome's options for the set instead, before the script: `--enable-blink-features=A,B` and `--disable-blink-features=C`, each a list of names separated by commas, which turn those features on and then off, so a feature that both name ends up off, as in Chrome. It refuses a name that is not a feature, and either option with `--session=`.

```text
$ out/runtime/mitto_page "'hasUAVisualTransition' in PopStateEvent.prototype"
true
$ out/runtime/mitto_page --disable-blink-features=HasUAVisualTransition "'hasUAVisualTransition' in PopStateEvent.prototype"
false
```

### Add an interface

An interface that Chrome exposes is on a Page already, from its table, with every member a Known Gap, so that its shape is Chrome's. A new Engine Release's interface gets a table with no change here, unless it uses a construct, a type or an extended attribute that the generator does not know, which stops the build with its name. To give an interface behaviour, give it a C++ class, which takes the place of its table:

1. Write its class in `native/dom/<file>.h` and `.cc`, where `<file>` is the interface's name in lowercase words, such as `pop_state_event` for `PopStateEvent`: `mitto::<interface>`, which derives from `bindings::ScriptWrappable`, or from its parent interface's class, and returns its generated `bindings::V8<interface>::kWrapperTypeInfo` from `GetWrapperTypeInfo()`. It has a static `Create()` with the constructor's arguments, if the interface has one, and a method for each member, named after the member, or after its `[ImplementedAs]`, with its first letter in upper case: `Type()` for an attribute `type`, `SetCancelBubble()` for its setter, and `InitEvent()` for an operation `initEvent`. A method takes the arguments of the IDL, converted: `bool`, `const std::u16string&` for a `DOMString`, a pointer to the class of an interface, a generated struct for a dictionary, `std::optional` for an optional argument without a default. One whose member is `[RaisesException]` takes a `bindings::ExceptionState&` last.
2. Add it to `mitto_bindings_interfaces` in [`native/bindings/interfaces.gni`](../native/bindings/interfaces.gni), with the members whose behaviour it does not have yet in `missing`, or those it has in `implemented`, and its files to [`native/dom/BUILD.gn`](../native/dom/BUILD.gn). Its parent interface needs a class first.
3. Build the Runtime. If the C++ writer refuses a type, an extended attribute or a construct that the interface uses, teach it in `cpp_types.py` or `cpp_writer.py`, following `bind_gen` for what a page sees.
4. Add the interface to the list in [`tests/runtime/chrome/probe.js`](../tests/runtime/chrome/probe.js), with an instance and any calls worth comparing, and to `_INTERFACES` in [`tests/test_page_bindings.py`](../tests/test_page_bindings.py). Then [record](#what-the-tests-compare-with-chrome) the Engine Release's Chrome again and run the tests.

## The document

A Page's scripts get a DOM of the Runtime's own, in [`native/dom`](../native/dom), whose classes follow Blink's, with Blink's checks and messages, and whose bindings the generator writes. Its nodes live on V8's C++ heap, as Blink's do on Oilpan: a node holds its parent, children and siblings with members on that heap, and its wrapper holds it through V8's wrapping, so a node and its wrapper live and die together, a detached tree lives as long as a script holds any of its nodes, and what a script put on a node's wrapper stays while the node lives.

### The window

The global object is a `Window`, made from `Window`'s template as Blink makes a window's context, so `window`, `self` and `globalThis` are the global proxy, its prototype chain is Chrome's, `Window.prototype`, then `WindowProperties` and `EventTarget.prototype`, and each is an immutable prototype, as Web IDL has it. `window`, `self` and `document` have their behaviour, and so do `navigator`, `screen` and the window's place and size below. `Window`'s other members are Known Gaps, and so is the named getter of `WindowProperties`, which would find elements by name.

What a page reads of the browser and the machine is what its Session sends, worked out by the same code or from the same data ([persona.md](persona.md#the-runtime)):

| A page reads | What it gives |
| --- | --- |
| `navigator.userAgent`, `appVersion` | The Session's `User-Agent`, and that without `Mozilla/` |
| `navigator.platform` | `Win32`, as Chrome on Windows gives, for a Persona of Windows |
| `navigator.language`, `languages` | The languages of the Session's `Accept-Language`, without their weights, as Chrome's language setting gives both, through Blink's `ParseAndSanitize()`, and the Persona's locale for none. `languages` is the same frozen array each time |
| `navigator.userAgentData` | A new object each time, as in Chrome. `brands`, `mobile`, `platform`, `toJSON()` and `getHighEntropyValues()`, which resolves from a task of its own, are the values of the Session's user agent client hints, read back from the Persona's own lines, with the Machine's platform version |
| `navigator.hardwareConcurrency`, `deviceMemory`, `maxTouchPoints` | The Machine's processors, memory and touch points, as `device-memory` sends the memory |
| `navigator.connection` | `effectiveType` as `ect` says, and the `rtt` and `downlink` that the renderer process of the document's site gives its host, which the library works out with the code of a subresource's hints. So it is what a `fetch()` from the document to its own host sends. about:blank's host is empty, and gets noise too, as in Chrome. `saveData` is `false` |
| `navigator.cookieEnabled`, `onLine`, `pdfViewerEnabled`, `webdriver`, `javaEnabled()`, `doNotTrack`, `vendor`, `product` and the rest of `NavigatorID` | What Chrome gives in a new profile: `true`, `true`, `true`, `false`, `false`, `null`, `Google Inc.`, `Gecko` |
| `screen.width`, `height` | The display over its scale, enclosed |
| `screen.availLeft`, `availTop`, `availWidth`, `availHeight` | The work area |
| `screen.colorDepth`, `pixelDepth`, `isExtended` | `24`, a display that is not HDR, and `false`, one display |
| `screen.orientation` | `portrait-primary` for a display at least as high as wide, and `landscape-primary` otherwise, at the angle 0. `lock()` rejects with Chrome on Windows' `NotSupportedError`, from a task of its own, and `unlock()` does nothing |
| `innerWidth`, `innerHeight` | The viewport |
| `outerWidth`, `outerHeight`, `screenX`, `screenY`, `screenLeft`, `screenTop` | The window's size and place |
| `devicePixelRatio` | The display's scale |

None of these values changes while a Page runs, so no `change` event comes, and the `onchange` handlers of `Screen`, `ScreenOrientation` and `NetworkInformation` are kept but never run. `navigator.plugins` and `navigator.mimeTypes` are Known Gaps until the C++ writer handles indexed and named property getters. The window's document is about:blank's, `<html><head></head><body></body></html>` in quirks mode, until the Page loads a document through its Session. The Page program given a script takes the document's markup with `--html=MARKUP`, and the script from standard input for `-`.

`mitto::NewPageContext()` makes such a context, and the Page program makes one for about:blank and one for each document that its Session loads. The window's timers, `queueMicrotask()`, `performance`, `fetch()` and `matchMedia()` have their behaviour, as [the event loop](#the-event-loop), [fetch()](#fetch) and [Media queries](#media-queries) say.

### Loading a document

Opening a Page with a URL navigates it, in [`native/page/document_loader.cc`](../native/page/document_loader.cc) on the Page's side and [`native/page_host.cc`](../native/page_host.cc) on the Session's. Everything that touches the network and cookies goes through the Session, as [ADR-0009](adr/0009-a-process-for-each-page.md) says:

- **What each Request Kind sends** is the Session's. Python gives the native Page what its Persona says a request of each kind sends, its header lines, priority and fetch parameters, when the Page opens. The library starts each of the Page's requests from that, with the same `RequestJob` and rules as a request of the C API's. So a Page's navigation sends what `session.get(url)` sends, and its script what `session.get(src, kind="script", initiator=url)` sends. A Page's requests run no timers, as Chrome's have none.
- **The Initiator** of a Page's request is its document, as the library loaded it: the URL that its navigation ended at, after redirects. The Page names the Kind, the URL and, for `fetch()`, what the script gives, but never an Initiator, so a Page cannot claim another site's Initiator to get that site's cookies, as Chrome's network service does not take a renderer's word for it. A Page at about:blank has no Initiator to give, so its requests fail with `ERR_ACCESS_DENIED`. A URL that is not HTTP or HTTPS fails with `ERR_UNKNOWN_URL_SCHEME`, and the Page goes on.
- **The navigation** is a request of Kind `navigation` with no Initiator. The library follows its redirects, as it does a request's, and sends the Page the final response, whose URL is the document's. A navigation that fails before a response leaves the Page at about:blank. A response that Chrome would not make a document of, such as a 204 or a download, still becomes one: a Known Gap.
- **The document** gets a new context, as Blink makes a new window for a tab's first navigation, whose about:blank has an opaque origin. Calls that wait for a promise of the old context fail, as DevTools says: `Execution context was destroyed.` The body is decoded as UTF-8, with a byte order mark dropped, and fed to the parser as it arrives, in pieces of up to 64 KiB. Charsets other than UTF-8 are a Known Gap, and so are documents of other types, which the parser reads as HTML.
- **Classic scripts** run in document order. One without `src` runs as soon as the parser reaches its end tag. One with `src` is fetched through the Session as Kind `script`, with the URL resolved against the document's, and the parser waits for it, as for a parser-blocking script, while other tasks run, such as scripts that the caller evaluates. What arrives of the document meanwhile waits, and the Session gets no credit for it until the parser takes it. A fetched script runs if its response has an ok status and a MIME type that Chrome runs as a script, and then `load` fires at its element. Otherwise, or when it cannot be fetched, `error` fires there, and the parser goes on. As in Chrome, a response with `X-Content-Type-Options: nosniff` whose type is no JavaScript type, and an image, audio, video or CSV one, does not run, with Chrome's console error that says why. A script with `defer` or `async` is fetched at once and runs after parsing, in document order, before `DOMContentLoaded`, a schedule that the HTML Standard allows, where Chrome's own comes with its preload scanner. What a script leaves uncaught reaches the Session as an uncaught error. A script with `nomodule`, a module script, a data block and scripts that the DOM inserts do not run: module scripts and inserted ones are Known Gaps. So are `<base>`, `document.currentScript` and charsets of scripts.
- **`document.cookie`** reads and writes the Session's cookies for the document's URL, as Chrome's `RestrictedCookieManager` does for a top-level page's script: a read gives no `HttpOnly` cookie, a cookie that a script sets is stored as one set by script, with `source_type` `"script"`, and a script cannot set an `HttpOnly` one. A read waits for the Session's answer, as Blink's does. A document that the Session did not load over HTTP or HTTPS, such as about:blank, has an opaque origin, so its `cookie` throws a `SecurityError`, as in a new tab of Chrome. The Page never sees an `HttpOnly` cookie's value: the response headers that it gets have no `Set-Cookie`.
- **Readiness**, in its simplest form: `document.readyState` is `loading` while the parser runs, `interactive` once it has finished, with `readystatechange`, then the deferred scripts run and `DOMContentLoaded` fires at the document, and in a later task it is `complete`, with `readystatechange`, and `load` fires at the window with the document as its target. Nothing else that a document loads holds `load` back yet. `DOMContentLoaded` reaches the document's listeners only: events that go through the tree and on to the window are a Known Gap.

### fetch()

A page's `fetch()` goes through the Session as a request of Kind `fetch`, with the document as its Initiator, on the same path as the document's scripts, in [`native/dom/fetch_loader.cc`](../native/dom/fetch_loader.cc) and [`native/page/page_fetcher.cc`](../native/page/page_fetcher.cc) on the Page's side:

- **What it sends.** `Request`'s constructor checks the URL, the method and the header lines as Blink's does, with Chrome's messages, normalizes the method and drops each forbidden request header, such as `Cookie`, as its `request` guard does. A string body adds `Content-Type: text/plain;charset=UTF-8`, and an `ArrayBuffer` or a view goes as its bytes. The library starts the request from the Persona's `fetch` lines, or from those of a fetch with a body, whose `Content-Type` stands where the Persona puts it, and the script's lines take the places of the Persona's lines of their names, with the rest after them, as a caller's `headers=` do. So `fetch(url)` from a page sends what `session.get(url, kind="fetch", initiator=page_url)` sends, and the Session's cookies go with a same-origin one.
- **What comes back.** `fetch()` settles once the response starts, with a `Response` whose status, reason phrase, URL, `redirected` and headers are the response's, never with a `Set-Cookie`, or rejects with `TypeError: Failed to fetch` when the request fails first. `text()`, `json()` and `arrayBuffer()` wait for the whole body, decode it as UTF-8 with a byte order mark dropped, and parse JSON with V8's `JSON.parse()`, so its `SyntaxError`s are Chrome's. A body that fails after the response started rejects them with `TypeError: Failed to fetch`.
- **Credit.** The body arrives in pieces of up to 64 KiB, and the Page gives the Session credit for them only once a script reads the body. So a large body that nothing reads holds the server back, as a full Mojo data pipe does in Chrome, and a `Response` that the garbage collector takes cancels the rest of its request.
- **Another origin.** A cross-origin `fetch()` has no credentials, as a page's does by default. Once any hop of a fetch goes to another origin than the document's, its response tainting is cors, and each response from then on, redirects included, has to pass the CORS check in the library before the redirect is followed or any of the response goes to the Page, as Chrome's network service does: `Access-Control-Allow-Origin` must be `*` or the document's origin, or `null` once a redirect from one other origin to another has tainted the request's origin. A response that fails fails the fetch. The library tells the Page the tainting, so the `Response`'s type is then `cors`, also after a redirect back to the document's origin, and its scripts read only the CORS-safelisted header names and those that `Access-Control-Expose-Headers` names. A request that would need a CORS preflight, such as one with a header line that is not safelisted, fails with `TypeError: Failed to fetch` and sends nothing to the other origin: the preflight is a request that no Persona records yet, a Known Gap until M8. So one that starts at the document's origin does not follow a redirect to another.

A `HEAD` request's response has a null body, as one with a null body status does: each read gives nothing, and the body is never used.

Known Gaps of `fetch()` in M6: `RequestInit`'s members beyond `method`, `headers`, `body` and `mode: "same-origin"`, such as `cache`, `redirect`, `referrer`, `credentials: "omit"`, `mode: "no-cors"` and `keepalive`, which throw when given a value other than their default, `credentials: "include"` for another origin, `AbortSignal`, a request too large for one message, with a body of nearly 16 MiB, which fails with `TypeError: Failed to fetch`, URLs that are not HTTP or HTTPS, such as `data:`, a body's stream, `clone()`, `blob()`, `formData()` and `bytes()`, and iterating over `Headers`.

### Media queries

`matchMedia()` parses its media query list with the CSS tokenizer and the media query parser in [`native/css`](../native/css), which follow CSS Syntax as Blink's `CSSTokenizer` runs it and Blink's `MediaQueryParser`, and which M9's CSS parser takes over. The fuzz target `media_query_fuzzer` feeds them any input. The `MediaQueryList` it gives writes the list back in `media` as Chrome writes it: lower case, Chrome's spacing, numbers with at most six significant digits, math functions simplified, `not all` for a query that does not parse, and a condition of a syntax that Blink does not know, Media Queries' `<general-enclosed>`, as it was given. Which media features parse follows the Page's runtime-enabled features, as in Blink: in the stable set of Chrome 157, `inverted-colors`, `prefers-reduced-data`, `video-dynamic-range`, `display-state` and `resizable` are experimental, so they do not parse, and a query of them is unknown and never matches, whatever the machine.

`matches` is worked out on each read, as Blink's `MediaQueryEvaluator` works it out for a tab of Windows Chrome, from what the Page's start message carries of the Session's Machine and Persona and nothing else:

| Media features | From |
| --- | --- |
| `width`, `height`, `aspect-ratio`, `orientation`, and the units `vw`, `vh`, `vmin` and the rest | The viewport |
| `device-width`, `device-height`, `device-aspect-ratio` | The display, over the scale, as `screen.width` and `screen.height` are |
| `resolution`, `-webkit-device-pixel-ratio` | The scale |
| `prefers-color-scheme`, `prefers-reduced-motion`, `prefers-reduced-transparency` | The three settings |
| `forced-colors`, `prefers-contrast` | The contrast theme: `active` and `more` with any theme a Machine can have, `none` and `no-preference` without one |
| `any-pointer` | `fine`, and `coarse` too with a touch screen. `pointer` is always `fine`, and `hover` and `any-hover` always `hover`: a desktop always has a mouse, which Windows reports even for a touchpad |
| `color`, `color-gamut`, `dynamic-range`, `monochrome`, `color-index` | 8 bits a channel, `srgb`, `standard`, 0 and 0: a Machine holds no wide-gamut or HDR display |
| `display-mode`, `scripting`, `update`, `overflow-block`, `overflow-inline`, `grid`, the viewport segments, `device-posture`, `scan` and the media types | What every tab of Windows Chrome has: `browser`, `enabled`, `fast`, `scroll`, a bitmap display, one segment, `continuous`, no `tv`, and `screen` |

Blink's parser recurses once for each parenthesis of a condition, as this one does, and Chrome 157 takes some 20,000 of them. So the Page program has the stack of Chrome's renderers on its main thread, 8 MiB, which on Windows its link sets as `chrome.exe`'s does, where Windows would give it 1 MiB.

A Machine does not change while a Page runs, so no `change` event is ever fired, as none would be in Chrome on that machine. `addListener()`, `removeListener()` and `addEventListener()` keep their listeners as any event target does, and a page can make its own `MediaQueryListEvent`. Blink keeps a list with change listeners alive while its document is, which only a `WeakRef` could tell apart.

Known Gaps of media queries:

- The math functions other than `calc()`, `min()`, `max()` and `clamp()`, such as `round()` or `sin()`, and a product or quotient of two dimensions, which Blink's typed arithmetic takes. A value with one does not parse, so its media feature is unknown, where Chrome computes it: `(width: round(10px, 3px))` is written back as given and never matches, where Chrome writes `(width: calc(9px))`.
- The units of the root element's font beyond `em` and `rem`: `ex`, `ch`, `ic`, `cap` and `lh` and their root forms take Blink's sizes for a document with no font data until the Runtime has fonts (roadmap, M9).
- `(fallback: none)`, a feature of container queries that Blink parses in a media query too and whose evaluation then stops Chrome's renderer, is unknown.

### The tree builder

The tree builder in [`native/dom/html_tree_builder.cc`](../native/dom/html_tree_builder.cc) takes the tokens of the HTML tokenizer in [`native/html`](../native/html) and builds a document's tree, or a fragment's for `innerHTML` and `outerHTML`, with the HTML Standard's tree construction for simple documents: the insertion modes from the start of a document to after its body, and the text of a script, a style, a title or a textarea. So `html`, `head` and `body` are made where a document leaves them out, elements, text, comments and the doctype go where the standard puts them, the doctype decides the quirks mode, and the end tags that elements such as `p`, `li` and `dd` imply close them. It switches the tokenizer for raw text, RCDATA, script data and plaintext, and drops a line feed after `pre`, `listing` and `textarea`, as the standard says. A Page runs scripts, so `noscript` holds raw text.

The rest of tree construction is M8's: the table insertion modes, templates, framesets, `select`, foreign content, processing instructions, and the list of active formatting elements with the adoption agency algorithm. A document that needs one still gets a tree, built as if the elements were ordinary ones, which may differ from Chrome's, and the builder records each rule it skipped. html5lib's tree construction tests read that record to tell a skipped rule from a wrong tree ([building.md](building.md#the-tree-builders-tests)).

## The probe

The probe records a page's **Script Fingerprint**: everything that the page's scripts can reach, and what the Persona and the Machine decide of it. It is [`tools/capture/probe.js`](../tools/capture/probe.js), and it runs unchanged in real Chrome, where [the capture kit's page](capture.md#its-recording-case) runs it for a **Baseline**, and in a Page, which a **Parity Check** gives it to. An indirect eval of it, `(0, eval)(source)`, gives a promise of its record as JSON's text, which the Page program prints and a Page's `evaluate()` returns. [`tools/capture/probe.py`](../tools/capture/probe.py) reads it. Until the Parity Checks of M7 replace them, M6's [`tests/runtime/chrome/probe.js`](../tests/runtime/chrome/probe.js) and its recordings stay as [above](#what-the-tests-compare-with-chrome).

It follows what [#207](https://github.com/darionxt/mitto/issues/207)'s walk of Chrome 155, 156 and 157 found, and uses only what V8 has, taken before it reads anything, so that it runs to its end in a Page that has few interfaces yet and goes on running as the bindings grow. It uses no regular expression, whose matches would change `RegExp`'s legacy statics, which it reads.

### What it records

1. **The walk.** From `globalThis`, breadth first, each object that it reaches, once, under the path where it found it first, such as `navigator.userAgentData`. An object reached only as another's `[[Prototype]]` gets its path last, so that `Function.prototype` is found as that and not as `Object`'s `[[Prototype]]`. For each object, its own properties in order, with their attributes, its `[[Prototype]]`, what `Object.prototype.toString` calls it, and for a function its `name`, `length` and source text where that is not `function NAME() { [native code] }`. A function whose own properties are only its usual `length` and `name`, as nearly every method and accessor is, is written where it is found. For an object that is neither a function nor a prototype, what each getter on it and on its prototype chain up to `Object.prototype` gives on it, and for a function what its own getters give, such as `Notification.permission`. A node of the DOM other than the document is written by its `nodeName` and not entered, so that no layout runs.
2. **The checks.** What each function, getter and setter of a prototype, and of an object whose `[[Prototype]]` is an interface's or a class's prototype, such as the window, throws when it is called on a new plain object, and what each constructor does without `new`. A promise that such a call gives is followed to what it settles with, once the microtasks queued before have run. The members of a namespace, such as `console`, `Math` or `CSS`, and the static members of an interface belong to no kind of object, so no check calls them.
3. **The values that the Persona and the Machine decide**, beyond what the getters give: `navigator.userAgentData.getHighEntropyValues()` with every hint, `matchMedia()` with each media feature that Blink's `media_feature_names.json5` names, which keywords and integers of each match, and whether the window's and the screen's sizes and `devicePixelRatio` agree with it, the resolved options of each of `Intl`'s constructors, how many values `Intl.supportedValuesOf()` gives of each kind, the time zone through `getTimezoneOffset()` on the first of each month of 2026 and `Date`'s strings of a winter and a summer day, the state of each permission that `navigator.permissions.query()` knows, and the lists of `document.featurePolicy`. Each call it waits for has a time limit of 5 seconds.
4. **What the page reported** to a `ReportingObserver` while the probe ran, which shows a getter or a check that queues a report.

The record holds `format`, `objects` with one entry for each object in the order found, `values` and `reports`. The probe's opening comment says what each holds, and how values and outcomes are written. Most checks throw `TypeError: Illegal invocation`, which the record leaves out, so that only the other outcomes take room.

### What it leaves out

- **Any other call.** It calls nothing that asks a person or opens something, such as `requestPermission()`, a picker, `getUserMedia()` or `window.open()`, and nothing else that follows the machine: fonts, canvas, WebGL and audio, which M9 and M10 bring, codecs and media capabilities, voices, the keyboard's layout, the battery, devices and their availability, such as `enumerateDevices()`, Bluetooth, USB, gamepads and XR, WebAuthn's authenticators, the storage estimate, and what `chrome.loadTimes()` and `chrome.csi()` return.
- **What it does not read, with why**, each in a list in the probe. The getters `window.fence` and `navigator.webkitPersistentStorage`, and `navigator.deprecatedRunAdAuctionEnforcesKAnonymity` of Chrome 155 and 156 without the variations seed, which queue a deprecation report when read (#207). The check of `Intl.v8BreakIterator` without `new`, which V8 still answers with a break iterator, and Chrome with a deprecation report. Each of these is in the record as skipped.
- **Promises that it finds.** It never waits for one, since some never settle, such as `navigator.serviceWorker.ready`. It handles each, so that one that is rejected is not reported as rejected with no handler.
- **Frames and workers**, which come with M8.

### What changes from run to run

The times, the navigation entry's random `key` and `id`, `navigator.connection`'s `rtt` and `downlink`, which #207 found, and `performance.memory`'s figures change between two runs of one Chrome. [The Normal Form of a Script Fingerprint](capture.md#the-normal-form-of-a-script-fingerprint) hides them, with the values that the machine decides, so that two records compare equal. `script_normal_form()` in [`script_normal_form.py`](../tools/capture/script_normal_form.py) writes it, and capture.md says what it hides and why.

### Its size

In Chrome 157.0.8103.39 on the Windows machine, from a user data directory with the variations seed at an HTTPS page at `capture.test`, it reaches 2,150 objects in about 100 ms, and gives the same record twice in a row but for the values above. Its record takes about 1.3 MB as `dumps_record()` writes it, with each property, getter's value, check and value of the third step on a line of its own, so that two records differ by lines, and so does its Normal Form. That is within the 1.5 MB that a Baseline of the Script Fingerprint may take for each Chrome Release, which the owner chose on 2026-11-12, for the first Recording Case. Later Recording Cases keep only what differs from the first. In a Page today it reaches about 250 objects.

[`tests/test_page_probe.py`](../tests/test_page_probe.py) runs it in a Page through a Session, and in the Page program, twice each, and checks that it runs to its end, leaves nothing in the console, and gives the same Normal Form.

## From Python

Until the release that ships the Runtime, Python's Page is private: `Session._open_page(url)` returns a Page that a `with` statement closes, and `await AsyncSession._open_page(url)` an AsyncPage that an `async with` statement closes. Neither is in `mitto.__all__` or in [api.md](api.md), and the release that ships the Runtime names them `open_page()`. On a Session whose library has no Page program beside it, as in a wheel that a release made, opening a Page raises a `NativeLibraryError` that says that the Runtime is not in this build. Starting the Page's process blocks for the few milliseconds that it takes, also on the event loop of an AsyncSession.

`_open_page(url, timeout=None)` navigates the Page to `url` through the Session, as [Loading a document](#loading-a-document) says, and returns once the window's `load` event has been dispatched. `timeout` is a number of seconds for that wait. A navigation that fails raises the `RequestError` that `session.get(url)` raises for that failure, and a timeout raises `PageTimeoutError`: either closes the Page first. `about:blank` navigates nowhere, as a new tab's first document needs no request. `url` is then the document's URL, after the navigation's redirects. The Page's scripts run in its document's context, which has V8's built-ins, its console and the interfaces that [the bindings](#the-bindings) have so far, with [timers](#timers) and [`fetch()`](#fetch).

- `evaluate(expression, timeout=None)` runs a script and returns its result as Python's `json` reads what `JSON.stringify()` writes, with `None` for what it writes nothing for. It waits for a promise to settle, as the Page program does. `timeout` is a number of seconds, as a request's total time is.
- `console_messages` holds what the scripts wrote to the console, each with its `level` and `text`, and `uncaught_errors` what a console says of each error that no script caught, for tests and debugging. Each keeps the last 1000, and fewer when their text is longer than 32 Mi characters, so that a Page that writes long messages cannot fill the caller's memory.
- `process_id` is the ID of the Page's process.
- `close()` ends the process and waits for it to go, which takes up to 2 seconds before a kill. An AsyncPage waits for that on a thread of its own.

A call fails with an error of `mitto._errors`, sorted by what a caller does next, as a request's are. Each is a `MittoError`, and private too:

| Error | What happened | What a caller does next |
| --- | --- | --- |
| `ScriptError` | The script threw, the promise that it gave was rejected, or its result cannot be read as JSON, such as a BigInt. The message is what a console says, such as `Uncaught TypeError: x is not a function` | Fix the script. The Page goes on |
| `PageEndedError` | The Page has ended: its process crashed, ran out of memory or was killed, broke the rules of the messages, or did not know its time zone or locale, or the Session closed. Each later call raises it again | Open another Page |
| `PageTimeoutError` | The timeout passed before the result arrived, or before the document loaded. It is a `TimeoutError` too | Wait longer, or close the Page: a script that never ends keeps it busy |
| A `RequestError` | Opening the Page: its navigation failed, as `session.get(url)` would have, such as a `ConnectError` | As for that request |

A Page that has been closed raises a `ValueError`, as a closed Session does. A Page waits for its events the way the Session's requests do. Page blocks in the native core with the GIL released, and several threads may use one Page: one of them at a time waits in the native core, and hands each the result that it waits for. Closing a Page while another thread waits ends that wait first, with `mitto_page_end_waits()`. An AsyncPage wakes when the Session's event descriptor, or its waiting thread on Windows, names the Page, and takes its events without waiting. A call takes at most 100 events before it looks for its result again, so that a Page that writes without end cannot keep it from its result or its timeout, or an AsyncPage hold up the loop. Closing the Session ends its Pages, whose calls then raise `PageEndedError`, and each still needs closing.

To run the tests of Pages against a local build, name the C test program and the Page program, which the tests copy beside the library:

```bash
export MITTO_CORE_TEST="$MITTO_WORKSPACE/chromium-<tag>/src/out/mitto/mitto_core_test"
export MITTO_PAGE_PROGRAM="$MITTO_WORKSPACE/chromium-<tag>/src/out/runtime/mitto_page"
uv run pytest tests/test_page_process.py tests/test_page_program.py
```

The tests in `tests/test_native.py` and `tests/test_page.py` that open a Page need the Page program beside the library that `MITTO_NATIVE_LIBRARY` names, as in a wheel, and skip without it.
